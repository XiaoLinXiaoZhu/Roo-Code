请求 1: [System Prompt] + [Message 1] + [Env 1] + [Message 2] + [Env 2]

## Prompt Caching 的本质

### 它缓存的是什么？

**不是缓存"对话轮次"，而是缓存"KV Cache"（Key-Value Cache）**

在 Transformer 模型中，处理输入时会计算每个 token 的 Key 和 Value 向量。这些计算结果可以被缓存。

### 为什么 ABCD → ABCDE 可以缓存？

```
请求 1: A B C D
        ↓ ↓ ↓ ↓
        计算 KV cache for [A, B, C, D]

请求 2: A B C D E
        ↓ ↓ ↓ ↓ ↓
        复用 [A, B, C, D] 的 KV cache，只计算 E
```

**关键**：ABCDE 的前缀 **完全等于** 之前的 ABCD

### 为什么 ABCD → ABCE 不能缓存 ABC？

```
请求 1: A B C D
        ↓ ↓ ↓ ↓
        计算 KV cache for [A, B, C, D]

请求 2: A B C E
        ↓ ↓ ↓ ↓
        ???
```

**问题**：虽然 ABC 相同，但缓存系统是按**完整前缀匹配**设计的。

### 技术原因

1. **缓存键是整个前缀的哈希**

    - 缓存键 = hash("ABCD")
    - 查找时用 hash("ABC") 找不到 hash("ABCD")

2. **实现复杂度**

    - 如果要支持"部分前缀匹配"，需要更复杂的数据结构（如 Trie）
    - 会增加查找开销

3. **Attention 机制的特性**
    - 在计算 D 的 attention 时，D 会"看到" A、B、C
    - 如果把 D 换成 E，E 看到的 A、B、C 的表示可能需要重新计算（取决于实现）

### 理论上可以做到吗？

**可以**，但需要更复杂的缓存策略：

```
缓存结构:
  "A" → KV for A
  "AB" → KV for A, B
  "ABC" → KV for A, B, C
  "ABCD" → KV for A, B, C, D
```

这样 ABCE 就可以复用 "ABC" 的缓存。但这会：

- 增加存储开销（每个前缀都要存）
- 增加查找复杂度

### Anthropic 的选择

目前的实现选择了**简单高效的完整前缀匹配**，而不是更复杂的部分匹配。
