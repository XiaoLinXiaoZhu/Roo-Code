- **记录 Y**：git diff 可恢复"做了什么"，但"为什么"只存在于上下文中

## 核心洞察

### 1. 信息不平等

对话中的信息重要性不同：

| 信息类型       | 重要性 | 时效性     |
| -------------- | ------ | ---------- |
| 任务目标/约束  | ★★★★★  | 全程有效   |
| 关键决策及理由 | ★★★★☆  | 长期有效   |
| 当前进度状态   | ★★★☆☆  | 阶段性有效 |
| 工具调用详情   | ★★☆☆☆  | 短期有效   |
| 对话噪声       | ★☆☆☆☆  | 即时失效   |

现有方案（总结/截断）对所有信息一视同仁，导致高价值信息和低价值信息同等概率丢失。

### 2. 源头结构化 > 事后提取

与其用 LLM 事后提取/总结（可能有偏差），不如在信息产生时就让它结构化：

- 工具调用记录：已结构化（100% 可靠）
- 文件变更：已结构化（git diff，100% 可靠）
- 关键决策/任务进度：混在对话中（需要提取，有偏差风险）

### 3. 记录 Y 而不是 X

**XY 问题**：用户想解决 Y（真正目标），但认为 X 是解决方案，于是问 X 怎么做。

如果文档记录的是「选择了什么方案(X)」而不是「要解决什么问题(Y)」，后续模型会被锁定在 X 上，无法在有更好方案时跳出来。

## 方案 2 的细化方向

将「关键决策」「任务进度」外部化到文档和 git 中，而不是保留在对话上下文里。

可能的文档类型：

- 需求/约束记录（记录 Y，不是 X）
- 执行计划（当前阶段、进度）
- 工作日志（发现、尝试、结果）

触发机制：

- 规则内化（system prompt / mode rules）
- 主动提醒（hints，基于 git 变更量等）
- 被动检查（completion 前检查）

## 深入讨论（续）

### 与 Checkpoint 的关系：互补而非替代

| 维度     | Checkpoint (代码快照) | Context Archive (认知快照) |
| -------- | --------------------- | -------------------------- |
| 记录什么 | 文件系统状态 (WHAT)   | 决策意图和进度 (WHY)       |
| 恢复什么 | 代码可以回滚          | 思维可以重建               |
| 触发时机 | 工具调用后自动        | 认知节点时主动             |
| 存储位置 | Shadow Git            | 项目文档                   |

**结论**：Checkpoint 解决"代码状态恢复"，Context Archive 解决"认知状态恢复"，两者正交互补。

### 核心概念：认知锚点 (Cognitive Anchor)

将"上下文归档"重新定义为"认知锚点"——在任务执行过程中的关键认知节点创建可恢复的思维快照。

### 文档结构设计

**位置**：项目级 `.task/` 目录（而非全局）

```
.task/
├── BRIEF.md          # 任务简报（记录 Y，不是 X）
├── PROGRESS.md       # 执行进度（当前状态）
└── DECISIONS.md      # 决策日志（可选，复杂任务）
```

**为什么是项目级**：

- 任务与项目强绑定，跨项目无意义
- 便于 git 追踪，可与代码一起版本控制
- 新对话启动时自动发现

### BRIEF.md 格式（强制 Y-first）

```markdown
# Task Brief

## Problem (Y) — 必填，先写

<!-- 描述要解决的根本问题，不是解决方案 -->
<!-- 问自己：如果有更好的方案，这个问题描述还成立吗？ -->

## Constraints — 必填

<!-- 技术约束、业务约束、时间约束 -->

## Approach (X) — 后写

<!-- 选择的解决方案，以及为什么选择它 -->
<!-- 明确标注：这是手段，不是目的 -->

## Success Criteria

<!-- 如何判断问题已解决 -->
```

### PROGRESS.md 格式

```markdown
# Progress

## Current Phase

<!-- 当前在做什么，下一步是什么 -->

## Completed

- [x] Step 1: ...
- [x] Step 2: ...

## Blocked / Pending

- [ ] Step 3: ... (blocked by: ...)

## Key Findings

<!-- 执行过程中的重要发现 -->

---

Last updated: {timestamp}
```

### 分层触发机制

```
Layer 1: 规则内化 (System Prompt)
├── 任务启动时：检查 .task/ 是否存在
├── 若存在：读取并恢复状态
└── 若不存在：创建 BRIEF.md（强制填写 Problem）

Layer 2: 被动检查 (Completion Guard)
├── attempt_completion 前：检查 PROGRESS.md 是否更新
└── 若未更新：提示更新后再完成

Layer 3: 主动提醒 (Hints) — 可选增强
├── 检测：git diff --stat 变更量 > 阈值
└── 提醒：建议创建认知锚点
```

| 机制     | 可靠性             | 侵入性 | 适用场景   |
| -------- | ------------------ | ------ | ---------- |
| 规则内化 | 中（模型可能遗忘） | 低     | 基础保障   |
| 被动检查 | 高（硬性门槛）     | 中     | 关键节点   |
| 主动提醒 | 高（系统触发）     | 高     | 长任务增强 |

### 任务完成后的文档处理

| 任务状态  | 处理方式                                                         |
| --------- | ---------------------------------------------------------------- |
| 成功完成  | → `docs/archive/{date}-{slug}/`，保留 BRIEF.md，精简 PROGRESS.md |
| 暂停/中断 | → 保持 `.task/` 原位，下次对话自动恢复                           |
| 失败/放弃 | → 用户选择：归档或删除，若归档则标注失败原因                     |

### 实施优先级

```
Phase 1: 基础能力
├── 定义 .task/ 目录结构
├── 编写 BRIEF.md / PROGRESS.md 模板
└── 在 System Prompt 中添加规则

Phase 2: 强化保障
├── 实现 Completion Guard
└── 与 Checkpoint 事件集成

Phase 3: 智能增强（可选）
├── 基于 git diff 的主动提醒
└── 自动归档流程
```

### 关键洞察

> **记录 Y 而不是 X** 的本质是：文档应该帮助未来的 AI（或人）理解"为什么要做这件事"，而不是"做了什么"。因为"做了什么"可以从代码和 git 历史中恢复，但"为什么"只存在于对话上下文中——这正是需要归档的核心信息。
