## 1. System Prompt（系统提示词）

### 核心发现

提示词写长写短、整洁还是乱，除非是直接指令，否则影响不大。当前 ~17k token 的推理链与 Cursor 量级相当。

### 工程经验正在被模型原生吸收

先读后写、问题追溯、工具调用方式等工程理念，模型已经逐渐内化。Subagent 也被特化训练——以前需要大量提示词说明使用方式、边界、信息传递，现在只要提一嘴"这是 subagent"模型就自己会调。

### 趋势：社区经验融入模型

类似 Qwen 图片模型的路径（preview 版 → 社区 LoRA → 正式版融合），大模型也在走这条路。MoE 架构下场景特调只影响一两个 expert，不影响整体智能。这也是为什么 OpenClawd 类产品能成功——从原生支持 tool call 到 agent 模式，都是工程特化的结果。

### 系统提示词中仍有价值的内容

1. **Local 事实**：环境信息（如 Windows）、用户偏好、项目特定信息
2. **主动推送信息**：用户懒得说的上下文
3. **非通用 trick 的教学**：模型无法使用 GUI debug 工具，需要教替代方法——如传递标记数据定位数据流向、远程 debug 写入本地文件实现 GUI 场景 debug。这类因环境限制产生的替代方法不属于通用工程经验，模型不会自然习得

### 设计方向演化

`do something`（直接指令）→ `role`（角色扮演）→ `soul document`（精神内核/价值观声明）→ **信息主导模式**（只提供完成任务所需的信息）。

**结论**：我们不再需要教模型太多东西，而是以"完成任务所需的信息"为核心设计方向。

## 2. 提示词设计模式

### 两个核心认知

1. **信息本位**：提示词的价值在于提供模型不知道的信息
2. **大模型是示例学习者，而不是真正的思考/推理者**

### 各模式的问题

- **Zero-shot 完全错误**：模型在实践中会忽略建议，仅遵守指令，且指令需要在对话序列末尾才不会被忽略。根本原因是没有将方法和实践结合到一起
- **传统 CoT 同样有问题**：使用人类思维演示推导路径，模型无法实际学习，尝试模仿只会给出拙劣的模仿——反而降低输出质量
- **Role、工程化等**：问题已在信息本位部分说过（教学内容正在贬值）

### 最佳实践

1. **70%+ 的 Few-shot**：示例使用 long-CoT 模式模拟遇到问题时的**真实思考路径**，包含反思、探索和振荡结构，而不是人类的逐步线性推理
2. **信息本位**：以模型不会知道的信息 / 主动推送的信息为主
3. **最佳格式**：
    - 示例用 `<example>` XML tag 包裹
    - Tool call 用 `toolname({"param": "value"})` 格式（具名函数 + JSON 参数），因为这符合模型的认知方式

## 3. 更好的工具

### 核心问题：为什么要包装为工具？

Tool Call vs CLI 的决策标准仅在于**输入输出的文本量**：

- **CLI**：输入少 且 输出为纯文本。优势是管道组合性（`grep | sort | head`）和 stdout/stderr 分离，模型有大量预训练经验
- **Tool Call**：输入多（尤其是长段文本）、或输出需要渲染到 UI、或需要创建特殊消息（如图片）。核心优势是**大量文本的输出**以及**模型原生支持的解析**——CLI 写入长文本需要引号包裹和转义处理，而 tool call 模型可以直接输出完整原始文本，各家的 markup language（如 ANTML）基本不会导致解析错误

### 工具分类

**可 CLI 化的工具**（输入少 + 输出纯文本）：

- `find_definition`、`find_usages`、`search_project`

**保留为 Tool Call 的工具**：

- 长文本输入：`edit`、`write_to_file`
- 子任务/UI 渲染：`apply_edit`、`consult_expert`、`build_tool`
- 特殊消息：`read_media`（图片）
- UI 交互：`ask_followup_question`、`attempt_completion`
- 内存状态 + UI：intent tree 系列工具

### 后续方向

朝着这个标准设计，大幅精简工具数量。

## 4. Agent-as-Tools

- **好也不好**：设计方向是对的，但因为模型内化现象（subagent 已被特化训练），这一步有点多余
- **优势**：可以通过 schema 实现更精准的派发；每个 agent 根据 schema 独立设计提示词后效果更好
- **总结**：agent-as-tools 是一个好的设计

## 5. XY Problem 与 Intent Tree

### 问题诊断

XY 问题的分析是准确的——多轮漂移在实际使用中占比非常高。但 Intent Tree 作为解决方案，**开销 >> 收益**，且没有达到设计上的高度。

### Intent Tree 为什么没达成目标

从第一性原理出发：Intent Tree 是一个**独立的、额外维护的数据结构**，和代码是分离的。维护它需要额外的 tool call，而这个维护本身没有直接产出。这就像让开发者在写代码的同时维护一份独立的设计文档——理论上很好，实际上没人做，因为它不在工作流的关键路径上。

实际使用中，intent tree 更像是一个"任务日志"，机械地记录做了什么，而不是真正区分约束和实现、也没有驱动力去抽象用户意图。

### 更好的方式：将意图融入关键路径

Intent Tree 最重要的一点是**将想法和代码实现绑定，使得每一个实现都能找到当初为什么做**。但实现这个目标不需要独立的数据结构：

1. **Git commit message 记录 Y**：commit 本来就在关键路径上，让 commit message 记录"为什么做"而不是"做了什么"，git log 本身就是 intent tree
2. **模块注释声明"为什么服务"**：在每个模块前声明自己为什么存在，意图直接写在代码里，和代码一起版本控制、一起被阅读，零额外维护成本

**结论**：intent tree 作为独立数据结构的方式开销过大，更好的方式是将意图融入已有的关键路径——git commit message + 模块注释。

### Reminder 工具：更好的长任务管理

Intent Tree 试图解决的另一个问题是"长任务中的上下文漂移"。Reminder 工具用更轻量的方式解决了这个问题：

1. **从"被动广播"到"主动预期"**：Todo List 每轮都在，模型每轮都忽略。Reminder 建立了"预期"——模型调用 `reminder(7轮)` 时，实际上是与自己签订契约："我预期在 7 轮内完成当前阶段"。触发时如果未完成，这本身就是强烈的反思信号
2. **解决上下文漂移**：Reminder 在时间轴上打桩，将无限延伸的对话流切分为有限的、有明确目标的片段。模型不再模糊地认为"我之前做了很多事"，而是清晰界定"在这个周期内，我完成了什么"
3. **Token 经济性**：相比每轮注入 Todo List，Reminder 只在到期时唤醒注意力。模型根据任务难度自主设定轮数（简单 3 轮，复杂 20 轮），实现计算资源的动态分配

## 7. Environment（环境信息优化）

优化方向正确且有价值，已落地的改动（XML 格式、目录树展示、相似文件折叠、.rooignore 控制）均为有效改进。

### Stage 2 更新：完全移除 Environment 注入

Environment details 作为 user message text block 注入，每次都会打断支持 Interleaved Thinking 的模型（如 GLM-4.7/5）的 reasoning 链路。已移除 `<vscode>`、`<git>`、`<workspace>`、`<terminals>`、`<recently_modified>` 注入，仅保留 `<intent_tree>`、`<todos>`、`<reminder>` 作为按需注入。无内容时不产生 user message，避免打断 thinking chain。
