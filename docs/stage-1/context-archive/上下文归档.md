## 上下文归档

### 当前实现

当前归档模式有两种：

1. 开启智能上下文压缩：当接近上下文长度限制时，调用llm总结对话内容，保留重要信息，然后重新开始对话
2. 关闭智能上下文压缩：当达到上下文长度限制时，直接截断最早的对话内容

#### 总结式归档

总结式归档最大的问题有两个：

1. 总结可能会产生偏差，导致后续工作重复历史工作内容
2. 总结需要额外腾出上下文，因为总结实际上同样依赖大模型生成，假设我们认为信息的压缩比为 4:1，那么总结会占用大约原始对话内容的 20% 的上下文长度（因为需要预留给模型生成总结）

#### 截断式归档

截断式归档的问题主要是丢失信息，尤其是当对话开始的内容包含重要决策时，直接阶段会导致模型不了解一开始是打算做什么，从而影响后续的行为。

## 未来方案

### 方案 1：智能折叠工具返回

现在比较常见的做法实际上是清理掉工具返回。将实际的工具返回使用占位符 【该工具返回结果已被折叠】

然后将工具返回单独存储在本地文件中，模型后续如果需要查看工具返回结果，可以通过检索本地文件来获取。或者重新调用工具。

### 方案 2：将工作模式改为可持续集成、可持续交付的流水线

核心要点为：

1. 将对话拆分为多个阶段，每个阶段有明确的目标和交付物
2. 每个阶段结束后，生成阶段总结和交付物，并存储在本地
3. 后续阶段可以基于前面阶段的交付物和总结来继续工作
4. 通过阶段划分和交付物管理，减少对话上下文的依赖

---

1. 这要求模型记住需要写报告、更新文档。
2. 要求模型通过 git 来管理代码和文档的变更。通过 git commit message 来记录每次变更的目的和内容。

---

可以通过 监控 git 情况，当检测到更改内容较多时，提示模型生成阶段总结和交付物。（通过 hints 提示模型）
