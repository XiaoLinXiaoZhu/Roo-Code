# 架构分析报告

> 基于架构参考文档与当前项目代码的深度对比分析

## 一、架构参考的核心理念总结

架构参考文档提出了以下关键工程原则：

1. **数据与提示词解耦**：使用 `DomainMessage` 联合类型作为 SSOT（单一事实来源），提示词是数据的"视图"（view），通过 `formatPrompt()` 映射
2. **工具参数类型集中定义**：工具接口在 shared types 中优先定义，避免反向依赖和 `any` 类型泛滥
3. **表达需求而非控制内部逻辑**：通过依赖注入不同的 client（creative/stable），而非在调用处传递 temp、repeatPenalty 等参数
4. **只追加的数据管理模式**：使用 SummaryMessage 等方式追加而非修改历史
5. **工具定义的扁平化**：参数扁平化、required 前置、利用参数顺序引导模型推理

## 二、当前架构的严重问题（第一性原则分析）

### 2.1 🔴 上帝类问题：Task.ts（4975行，69个imports，~130+独立方法）

**这是整个项目最严重的架构问题。**

Task.ts 承担了至少 6 类不同的职责：

- API/模型交互（43个方法）
- 消息管理（53个方法）
- 工具执行协调（16个方法）
- 状态管理（14个方法）
- UI/WebView 通信
- 文件/持久化

构造函数接收 20 个参数。这意味着 Task 类是一个巨大的上帝对象，几乎所有模块都直接依赖它。

**从第一性原则来看**：一个类应该只有一个变化的原因（SRP）。Task.ts 有至少 6 个变化原因——修改 API 调用逻辑、修改消息格式、修改工具执行、修改状态机、修改 UI 通知、修改持久化方式——任何一处变更都需要在这个巨型文件中操作。

### 2.2 🔴 Anthropic SDK 类型泄漏：全项目耦合

```
ApiHandler.createMessage(
  systemPrompt: string,
  messages: Anthropic.Messages.MessageParam[],  // ← Anthropic 类型作为核心接口
  metadata?: ...
): ApiStream
```

**58 个文件**直接使用 `Anthropic.*` 类型，其中大量位于 `core/`、`shared/`、`utils/` 等本不应关心具体 SDK 的模块中。

这正是架构参考中批评的**"将 ModelMessage 作为数据载体"**的反模式。当前项目使用 `Anthropic.Messages.MessageParam` 作为系统中消息流转的通用类型，导致：

- 所有 Provider 必须将消息转换为 Anthropic 格式
- 非 Anthropic 提供者（OpenAI、Gemini 等）需要额外的 transform 层做二次转换
- 业务逻辑中充斥着 Anthropic 特有的类型约束

### 2.3 🔴 严重的双向循环依赖

检测到 **11 对双向依赖**关系：

```
core/task ↔ core/tools       (40+4 = 44 imports)
core/task ↔ core/webview     (3+2 = 5 imports)
core/task ↔ core/assistant-message
core/task ↔ core/environment
core/task ↔ core/checkpoints
core/task ↔ core/message-manager
core/task ↔ integrations/editor
core/tools ↔ core/prompts
core/webview ↔ services/mcp
core/webview ↔ services/skills
core/webview ↔ integrations/workspace
```

`core/task` 与 6 个模块存在双向依赖，说明 Task 既被依赖，又反向依赖了几乎所有核心模块。这使得模块无法独立测试、独立演进。

### 2.4 🟠 缺少统一的领域消息模型（DomainMessage）

当前项目使用两套并行的消息系统：

- `ClineMessage`（面向 UI 的 ask/say 消息，定义在 `@roo-code/types`）
- `Anthropic.Messages.MessageParam`（面向 API 的消息）

**没有一个统一的、与提供商无关的领域消息类型**。这导致：

- UI 层和 API 层使用不同的消息模型，需要手动同步
- 无法对同一事件有一个唯一的记录源
- 持久化时需要分别保存两套消息（`apiConversationHistory` 和 `clineMessages`）

### 2.5 🟠 工具定义分散，存在反向依赖

`presentAssistantMessage.ts` 直接 import 了 **30+ 个工具实例**，形成巨大的 switch/if 分发逻辑。虽然有 `BaseTool` 抽象和 `toolRegistry`，但工具的 schema 定义和 prompt 定义分布在两处：

- `src/core/prompts/tools/native-tools/` — 提示词中的工具描述
- `src/core/tools/` — 工具的实际执行逻辑

工具参数定义（`toolParamNames`）是一个巨大的字符串数组，缺乏类型安全的参数定义结构。

### 2.6 🟡 API 参数直接透传模式

当前 `ApiHandlerCreateMessageMetadata` 包含了 `tools`、`tool_choice`、`parallelToolCalls` 等底层参数，业务逻辑需要关心这些 OpenAI 特定的概念。这与架构参考中"表达需求而非控制内部逻辑"的原则相违背。

## 四、逐步迁移建议

### Phase 1: 解除 Anthropic 类型耦合（优先级最高）

**目标**：定义项目自己的 `DomainMessage` 联合类型，替代 `Anthropic.Messages.MessageParam`

1. 在 `@roo-code/types` 中定义 `DomainMessage` 联合类型：

    ```typescript
    export type DomainMessage =
      | SystemMessage
      | UserTextMessage
      | AssistantTextMessage
      | AssistantToolCallMessage
      | ToolResultMessage
      | SummaryMessage
      | ...
    ```

2. 创建 `formatForProvider(messages: DomainMessage[], provider: string): ProviderMessages` 适配层

3. 修改 `ApiHandler.createMessage` 接口，接收 `DomainMessage[]` 而非 `Anthropic.Messages.MessageParam[]`

4. 逐步将 58 个使用 `Anthropic.*` 类型的文件迁移到 `DomainMessage`

**预计影响**：~58 个文件，建议分 3-4 个 PR 完成

### Phase 2: 拆分 Task 上帝类

**目标**：将 Task.ts 从 4975 行缩减到 < 500 行

建议拆分为：

- `TaskOrchestrator` — 核心编排逻辑（状态机 + 主循环）
- `ConversationManager` — 消息管理（已有 `MessageQueueService` 基础）
- `ApiClient` — API 交互封装
- `TaskStateStore` — 状态持久化（已有 `TaskHistoryStore` 基础）
- `ToolExecutor` — 工具执行协调（已有 `toolRegistry` 基础）

**迁移策略**：Extract Method → Extract Class，逐步将方法移出 Task

### Phase 3: 统一工具定义系统

**目标**：工具 schema、参数类型、执行逻辑统一注册

1. 在 `@roo-code/types` 中定义完整的 `ToolCallRecord` 和 `ToolResult` 联合类型（参照架构参考）
2. 将 `presentAssistantMessage.ts` 中的 switch 分发替换为 registry 查找
3. 合并 prompt 工具描述和工具执行逻辑的定义源

### Phase 4: 消除循环依赖

**目标**：所有模块间依赖为单向 DAG

1. 引入事件总线（EventBus）解耦 Task ↔ WebView
2. 使用接口而非具体类型打破 Task ↔ Tools 循环
3. 将 Task 的公共属性提取为 `TaskContext` 接口，工具依赖接口而非 Task 类

### Phase 5: API 参数抽象

**目标**：业务逻辑不再关心底层模型参数

1. 定义 `GenerationPreset` 枚举（`stable` / `creative` / `balanced`）
2. 在 Provider 层面将 preset 映射为具体参数
3. 业务逻辑仅选择 preset，不传递 temp 等参数

## 五、总结

当前项目面临的核心架构问题可以归纳为一个根因：**缺乏明确的领域模型层**。

项目在快速迭代中，将 Anthropic SDK 的类型体系作为了事实上的领域模型，Task 类作为了事实上的"应用核心"，导致所有模块都直接耦合到这两个支点上。

架构参考提出的 DomainMessage + formatPrompt 模式，本质上是在说：**先定义"我们的世界长什么样"（领域模型），再决定"如何向外界描述它"（视图/适配）**。这是值得采纳的核心架构理念。

迁移建议的优先级排序：

1. 🔴 **定义 DomainMessage**（解耦 Anthropic SDK） — 影响最大，是后续所有改进的基础
2. 🔴 **拆分 Task 类** — 可与 Phase 1 并行推进
3. 🟠 **统一工具定义** — 在 Phase 1 基础上自然推进
4. 🟡 **消除循环依赖** — 随着 Phase 1-3 的完成会自然改善
5. 🟢 **API 参数抽象** — 收益明确但优先级可后置
