前言
这篇文章主要聚焦于如何构建一个 ai 原生应用——而不是仅仅将ai集成到已有程序中，包含了一些个人的实践经验、偏好等。
因为我个人使用 ts 开发，所以说本文中的示例大部分使用 ts 编写。

工程建议
数据一定要和提示词实际组织解耦
之前看大部分ai应用或者ai工具开发的时候，常常会看见类似：
function callTool(args: any): Promise<string>
// 或者
function callTool(args: any): Promise<ToolResult>

// 然后内部处理工具，最终将结果组织为一个string或者类似 {role,content} 的返回。
这种内部直接使用 ModelMessage 记录所有事件，通过它里面已有的字段加上自己附加一些metadata的方式做数据流转等的模式。
这是严重的耦合，数据和提示词实际组织本质并不相关。后续想要做数据持久化或者其他进一步的操作（比如说ui显示等），需要费很大的力气去传递参数或者解析。
正确的模式应该是，将 提示词 视作数据的一个 视图（view），而数据只负责用于记录当时发生了什么。
始终以数据作为 SSOT(Single Source of Truth)。其他的模块始终围绕着数据进行操作。
比如比较通用的做法是，定义一个巨大的联合类型，比如n0n中：

// ── 系统消息 ──
export interface RawSystemMessage {
type: "system";
content: string;
}

// ── 用户消息 ──
export interface RawUserTextMessage {
type: "user_text";
content: string;
}

/\*_ 真实用户输入（交互模式），adapter 负责包装为设计线索并拼接上下文 _/
export interface UserInputMessage {
type: "user_input";
content: string;
context: string | null;
hint: string | null;
}

// 省略...

export type DomainMessage =
| RawSystemMessage
| RawUserTextMessage
| UserInputMessage
| UserImageMessage
| AssistantTextMessage
| AssistantToolCallMessage
| ToolResult
| IdleNudgeMessage
| TurnFeedbackMessage
| ReminderDueMessage
| SubmitRejectedMessage
| ToolArgErrorMessage;
然后上下文从这个唯一的数据来源进行map：
export function formatPrompt(
messages: DomainMessage[],
options
): PromptMessage[]
内部仅仅需要关心业务逻辑，外部处理具体的提示词组织和格式化。
一个潜在的优势就是可以根据不同的模型定制不同的提示词风格。
举个例子，比如使用 anthropic 模型，因为claude拥有较强的环境感知能力，简单将信息平铺展示即可，只需要保证对于模型来说组织易读。
而对于 openai 模型，因为openai更“专注”于目标，所以说仅仅是平铺展示效果较差，应该提供指令要求模型对提供的信息进行处理。
工具参数定义
工具的参数定义一定要放在 share 的 types 定义中，而不应该在具体的工具实现中定义。否则将会出现很严重的反向依赖和大面积的any和转换。
永远不要手动抄写和同步类型定义，永远确保一样的东西只在一个地方定义一次，如果它们不同，则应该取不同的名字或者放在完全隔离的模块中。
工具的实际执行逻辑和 tool schema 可以放在别处处理，但是接口一定是优先定义的。
一个简单的示例：
interface ToolCallBase {
id: string;
}

export type ExecToolCall = ToolCallBase & { tool: "exec"; args: ExecArgs };
export type WriteToolCall = ToolCallBase & { tool: "write"; args: WriteArgs };
export type EditToolCall = ToolCallBase & { tool: "edit"; args: EditArgs };

export type ToolCallRecord =
| ExecToolCall
| WriteToolCall
| EditToolCall

// ── 工具结果 ──
// 每个 Result 嵌入原始 ToolCall（call 字段）。
// call = LLM 原始调用参数；顶层字段 = 执行产出。
// tool 字段与 call.tool 始终一致，用于判别联合窄化（TS 不支持嵌套属性窄化）。

interface ToolResultBase {
type: "tool_result";
}

export type ExecToolResult = ToolResultBase & {
tool: ExecToolCall["tool"]; // "exec"
call: ExecToolCall;
exitCode: number;
stdout: string;
stderr: string;
durationMs: number;
};

export type WriteToolResult = ToolResultBase & {
tool: WriteToolCall["tool"]; // "write"
call: WriteToolCall;
success: boolean;
error: string | null;
};

export type EditToolResult = ToolResultBase & {
tool: EditToolCall["tool"]; // "edit"
call: EditToolCall;
diff: EditDiff;
success: boolean;
error: string | null;
};

export type ToolResult =
| ExecToolResult
| WriteToolResult
| EditToolResult
从而，在 DomainMessage 和全局的类型定义的基础上，不论是ui还是逻辑处理，都能轻松处理各种情况。
当一处进行修改，其他的地方能够联动修改、或者至少类型检查报错，而不是错误隐藏。
准确表达需求，而不是直接控制内部逻辑
很多使用我们有一些需求，想要控制模型传入的参数比如：

- 对于严格匹配替换或者摘要、引用，我们可能希望尽可能的降低模型的温度以保证输出的一致性。
- 对于一些开放性的问题，我们可能希望提高温度、同时增加重复惩罚。
  然后很多时候代码就会出现：
  generateResponse(
  model,
  messages,
  temp: 0.1,
  repeatPenalty: 1.2,
  )
  或者
  generateResponse(
  messages,
  options: {
  model,
  temp: 0.1,
  repeatPenalty: 1.2,
  }
  )
  但是实际上需要思考的事情是：内部真的需要关心这些参数吗？
  内部的业务逻辑的诉求很简单：我需要在稳定和创造模式之间切换。
  于是实际上只需要依赖注入不同的client，不同的client内部实现做出差异：
  const creativeClient = new Client({
  temp: 0.8,
  repeatPenalty: 1.2,
  })

const stableClient = new Client({
temp: 0.1,
repeatPenalty: 1.2,
})
通过依赖注入提供不同的client，从而让内部仅仅需要关心业务逻辑，而不是具体的参数（还窄化了接口）。同时不同client可以有自己的实现细节，不论是使用不同的服务提供商还是使用一些神秘魔法啥的。
// 注入 stableClient 作为 client
client.generateResponse(
messages
)
数据管理模式
始终使用只追加的模式管理数据（比如 DomainMessage），而不是直接修改历史。
比如，对于一个对话，它的上下文达到了上限，此时需要对其进行总结和摘要。
比较好的做法是添加一个 SummaryMessage，作为替换的anchor，而不是直接修改历史。
比如：
const summaryMessage : SummaryMessage = {
type: "summary",
summary: summaryHistory(messages),
}

messages.push(summaryMessage)
然后，在 formatPrompt 中，仅仅需要简单处理即可，使用summary的内容替换它之前的 user - assistant 循环。
模型侧 tricks
提示词撰写的一些基本原则
提示词基础规范
工具定义 其一
按照 openai 的约定，工具定义的标准格式为：
{
"type": "function",
"function": {
"name": "function_name",
"description": "function_description",
"parameters": {
"type": "object",
"properties": {
"property_name": {
"type": "string",
"description": "property_description"
}
},
"required": ["property_name"]
}
}
}
需要注意的是服务提供商往往直接将该json format 一下直接注入系统提示词末尾。这就意味着实际上、参数顺序将会影响最终的输出。
这里有两个层级的理解：

1. parameters 的参数顺序：
   当你发现尽管申明了required，模型仍然会忘记传入这些参数，可以考虑将required放在最前面，类似：
   {
   "type": "function",
   "function": {
   "name": "function_name",
   "description": "function_description",
   "parameters": {
   "required": ["property_name"],
   "properties": {
   "property_name": {
   "type": "string",
   "description": "property_description"
   }
   }
   }
   }
   }
2. property_name 的顺序：
   模型往往会按照工具定义的顺序填写参数，这意味着，越是需要推理、越是需要分析的参数，应该放在后面。
   比如 edit 工具中，应该让模型先宣告自己想要修改哪个文件，然后才是具体的内容。
   工具定义 其二
   模型调用工具本质上是输出一个包含模型特定的token的xml like结构。
   服务提供商对其进行解析、然后将其提取出来放在 tool_calls 字段中。
   这意味着一个优势：因为模型一般会有一些自定义的token去定义标记xml结构，也就是说，它不需要担忧解析的问题。同时也没有转义的问题（因为它使用xml like 进行标记）。这对于长段文本非常友好。
   但是这同时意味着一些劣势：
3. 模型不擅长输出嵌套的数据结构或者是是数组。
   模型想要输出这类结构，有两种模式：

- 使用类似 xml 的结构，进行嵌套，而数组则转换为 xml 的数组结构。例如：
  <parameters name="list" type="array">
  <item>item1</item>
  <item>item2</item>
  </parameters>
- 使用类似 xml like 和 json 混合的结构，比如数组处理为：
  <parameters name="list" type="array">
  [
  "item1",
  "item2"
  ]
  </parameters>
  这启发我们将参数尽可能扁平化，而不是嵌套。如果我们确实需要list类型的输出可以考虑两种模式：
- 让模型多次调用一个工具
- 我们自定义一个轻量的DSL（Domain Specific Language），比如要求模型输出markdown。然后再从这个markdown中解析出list。

2. 模型不擅长处理细碎的参数。
   如果一个工具的参数过多，模型可能会对该工具的调用效果较差，考虑的优化可以是：

- 参考 工具schema 中，将 require 提前，让模型更多关注必填的参数。
- 如果你的参数都是一些flag或者简单的选择，不包含长文本，可以考虑使用类似 cli 的模式，让模型输出单行的命令，比如：--flag1 --flag2。
