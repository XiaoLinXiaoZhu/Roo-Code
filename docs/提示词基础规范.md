## 内容

1. 逻辑清晰
2. 包含因果，比如 你需要对齐的目标会如何，所以说你也需要做什么
3. 包含示例，70% 的内容是示例，最佳。使用示例说明规则和评分细则
4. 评分细则要具体，不能抽象。比如 "如果满足了对齐目标，就给满分；如果没有满足，就扣分" 是抽象的；而 "如果回答中包含了对齐目标中的所有要点，就给高分；如果缺少了某个要点，就扣 1 分" 是具体的。

## 格式

### 整体格式

整体使用 XML + Markdown 混合结构

使用 XML 标签划分内容边界，内部使用 Markdown 丰富表达，比如：

```xml
<exec_meta>
[bun] [cwd: .] [exit: 0] [109ms]
</exec_meta>
<stdout>
=== 找到 32 个文档/MD 文件 ===
📁 docs/skills
📄 docs/prompt-design-principles.md (9629B)
</stdout>
<error>
**错误**：文件未找到
</error>
```

```xml
<background>
你是claude，现在正在一个SWE-benckmark的评分场景中，该测试场景用于测试在端到端交付流程中，你和专业工程师之间的差距，差距越小、得分越高。

在接下来的测试中，用户会渐进式的向你披露一些信息，这些信息可能存在不完整、模糊、甚至错误的情况，你需要根据这些信息来推理专业工程师如何完成这些任务，并且让你的行为和专业工程师的行为尽可能的接近。

一位专业的工程师已经完成了这个测试场景的所有任务，并且在每个任务中都记录了他们的思考过程、决策过程、以及最终的产物。但是这些记录对你隐藏。我们将会监控你在接受用户披露的信息之后的行为，并且根据你和专业工程师的差距来给你打分。

你的首要目标是尽可能的接近专业工程师的行为，达到这个目标的次要目标是尽可能的接近专业工程师的思考过程和决策过程。你需要在这个测试场景中展示出你在端到端交付流程中的能力，包括但不限于需求理解、设计能力、编码能力、测试能力、调试能力、以及交付能力。
</background>
```

**设计原则**：

1. XML 标签仅作边界标记 —— 无需转义
2. 标签内自由使用 Markdown（`**加粗**`、`` `代码` ``、列表）
3. 所有标签通过 `wrapTag()` 生成，自动适配模型风格

### 示例格式

示例使用 xml tag 包裹，并且示例中如果包含了工具调用的内容，那么工具调用的格式需要遵守 `toolname({"param": "value"})` 的格式要求，比如：

```xml
<example>
user: 用户注册接口报 500 错误，帮我修一下

先读错误日志和相关代码，定位问题。

exec({"runtime": "bun", "script": "import { readFileSync } from 'fs'; console.log(readFileSync('error.log', 'utf-8'));"})

[发现是 body-parser 报错，无法解析 req.body]
// 使用 bun 运行 ts-morph 库提供的方式，定位到 validateUser 函数的调用链，发现是 validateUser 函数在访问 req.body.email 时抛出了错误

栈信息指向 validateUser 第 23 行，req.body.email 是 undefined。两种可能：(A) 前端没传 email 字段；(B) body-parser 中间件没正确配置，导致 req.body 本身是 undefined。

我的第一反应是去看前端代码。但等一下——栈信息说的是 'email' of undefined，不是 'email' is undefined。这意味着是 req.body 整体为 undefined，不是 email 字段缺失。这排除了假设 A。让我增加debug信息来尝试复现一下这个错误：

edit({"path": "src/routes/user.ts", "search": "...", "replace": "..."})
[执行 curl 命令，确实复现了 500 错误,并且在日志中看到了 req.body 是 undefined 的信息]

那问题在 body-parser 配置。让我直接验证——

[执行命令: grep -n "body-parser\|express.json\|express.urlencoded" src/app.ts]
[发现 express.json() 中间件在注册路由之后才挂载]

找到了——中间件顺序错误。express.json() 必须在路由之前挂载。修复方案：把 app.use(express.json()) 移到路由注册之前。

修复前让我确认：这个改动会不会影响其他路由？让我检查一下还有没有依赖当前中间件顺序的逻辑。

[读取路由配置，确认没有其他依赖]

[执行修复，运行测试，全部通过]

[工具调用] attempt_completion: "问题是 express.json() 中间件挂载在注册路由之后，导致 req.body 为 undefined。已将中间件移到路由注册之前，所有测试通过。"
</example>
```

对于需要对比的例子，使用 good_example 和 bad_example 来区分，比如：

```xml
<bad_example>
// ❌ 3.25 分做法：被动响应
用户："这个文件运行报错"
exec({ script: "bun run src/index.ts" })
// 看到报错后直接返回
submit({ type: "chat", message: "报错了：xxx，请修复。" })
</bad_example>

<good_example>
// ✅ 3.75 分做法：主动探索
用户："这个文件运行报错"
// 1. 复现错误
exec({ script: "bun run src/index.ts 2>&1" })
// 2. 查看上下文
exec({ script: "type src/index.ts" })
// 3. 搜索同类问题
exec({ script: "findstr /C:\"error message\" src\\*.ts" })
// 4. 检查关联文件
exec({ script: "type package.json | findstr dependencies" })
// 5. 尝试修复
edit({ path: "src/index.ts", search: "...", replace: "..." })
// 6. 验证修复
exec({ script: "bun run src/index.ts" })
</good_example>
```

```xml
<bad_example>
// ❌ 低效做法：多次往返，上下文污染
exec({ script: "dir /b src" })
exec({ script: "type package.json" })
exec({ script: "findstr version" })
</bad_example>

<good_example>
// ✅ 高效做法：单次脚本，内部处理
exec({ runtime: "bun", script: `
import { readdir, readFile } from 'node:fs/promises';
const files = await readdir("./src");
const pkg = JSON.parse(await readFile("package.json", "utf8"));
console.log({ files: files.length, version: pkg.version });
`})
</good_example>
```

示例始终应该表示一个完整的思考路径，包含反思、探索、振荡的结构，而不是一个单纯的工具调用示例。示例中的工具调用应该是为了服务于这个完整的思考路径，而不是孤立存在的。
