## 工具描述优化

与其在描述中要求做a做b，不如直接在schema中要求输出。当前工具描述中有很多"指导原则"，但这些只是建议，模型可能不会遵循。

将这些"思考过程"转化为必填参数，可以：

1. 强制模型在调用前进行结构化思考
2. 让思考过程可见、可审查
3. 提高工具调用质量

这样可以强制模型在咨询前梳理清楚相关的信息。

同时可以大幅度简化工具描述，只保留必要的信息，减少冗余。

## 最好的方式

最好的方式是在工具描述中说明该工具的用途和功能，并且基于调用示例。而将思考、质量要求写入调用schema中，将选择和思考分开。

- **工具描述**：只用来提供选择信息（我要不要用这个工具）
- **Schema 参数**：用来提供思考指导（我该怎么用这个工具）

## 实践案例：`ask_followup_question` 工具优化

### 优化前

```typescript
const ASK_FOLLOWUP_QUESTION_DESCRIPTION = `Ask the user a question...

**When to Use (Spirit-Aligned)**:
1. **Goal Discovery (Result Orientation)**
   - When user's request (X) is unclear about the true goal (Y)
   - Present possible goals with their consequences to help user choose
   - Example: "Virtual scrolling can solve several problems..."

2. **Honest Uncertainty (Radical Honesty)**
   - When you're uncertain and need user input to verify
   - This is your "third option" - instead of guessing, ask
   ...

**How to Ask Well**:
- Always provide 2-4 suggested answers with consequences
- Each suggestion should be complete and actionable
...`

// Schema 只有 2 个参数
parameters: {
  question: string,
  follow_up: [{ choice, affect }]
}
```

**问题**：

- 工具描述冗长，混入了大量"指导原则"
- 这些原则只是建议，模型可能不遵循
- 无法强制模型思考"为什么要问"

### 优化后

```typescript
const ASK_FOLLOWUP_QUESTION_DESCRIPTION = `Ask the user a question...

**When to Use**:
- goal_discovery: User's true goal (Y) is unclear from their request (X)
- honest_uncertainty: You're genuinely uncertain, asking is your "third option"
- passive_verification: Active verification (experiments/scripts) is not possible

**Example**:
{
  "type": "goal_discovery",
  "question": "Virtual scrolling can solve several problems. Which one are you facing?",
  "follow_up": [
    {"choice": "Performance - scrolling is laggy", "affect": "Virtual scrolling is correct"},
    {"choice": "Slow initial load", "affect": "Pagination might be simpler"}
  ]
}`

// Schema 新增 type 参数（enum）
parameters: {
  type: enum["goal_discovery", "honest_uncertainty", "passive_verification"],  // 新增
  question: string,
  follow_up: [{ choice, affect }]
}
```

**改进**：

- 工具描述简洁，只有用途 + 示例
- 新增 `type` 参数（enum），强制模型分类提问原因
- 对于 instruct 模型，enum 参数能有效引导思考

### 设计决策

**为什么用 enum 而不是自由文本？**

- enum 强制分类，避免模型随意填写
- 便于后续审计和分析
- 对 instruct 模型有更强的约束力

**为什么不加 `context` 参数？**

- 专家分析指出：自由文本参数容易变成"废话生成器"
- 真正的上下文分析应在 system prompt 的 `<thinking>` 中完成
- 保持 schema 简洁，只添加有明确价值的参数

## 修改工具时的联动清单

修改工具定义后，需要同步更新以下文件：

### 1. 类型定义

- **`src/shared/tools.ts`**
    - `toolParamNames`：添加新参数名
    - `NativeToolArgs`：更新工具的类型定义
    - `XxxToolUse` 接口：更新 params 类型

### 2. 参数解析

- **`src/core/assistant-message/NativeToolCallParser.ts`**
    - `createPartialToolUse` 中的 case 分支：处理流式解析
    - `finalizeStreamingToolCall` 中的 case 分支：处理完整解析

### 3. 工具执行

- **`src/core/tools/XxxTool.ts`**
    - 参数接口定义
    - `execute` 方法中的参数解构

### 4. 测试文件

- **`src/core/tools/__tests__/xxxTool.spec.ts`**
- **`src/core/assistant-message/__tests__/presentAssistantMessage-*.spec.ts`**
- 其他引用该工具的测试文件
