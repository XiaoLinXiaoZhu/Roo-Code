## 情景

有的时候我们需要快速构建一些工具，之后使用这些新构建的工具将能够帮助我们快速的完成一些任务，比如说：

- 现在我在游戏测试场景，我需要频繁的去游戏界面抓取窗口以检查游戏内容是否正确显示
- 现在我需要对一张大的图片进行分析，我需要将图片的局部进行切割和放大以便于查看各个部分的细节

---

这种问题大多数都是：

- 边界明确、功能单一
- 需要提供稳定的运行、需要测试验证工具效果
- 需要最大的兼容性，可以通过传参数或者配置文件进行配置
- 可以使用管道操作来进行工具的组合

但是现在的问题就是，即使是这类工具，模型往往不会意识到它们需要这个工具，因为按理来说，使用已有的工具手动执行这些任务并不困难。但是问题就在于这类事情的累加上，这将会持续不断的为模型增加认知负担，从而影响模型的整体表现。

最期望的情况是，当模型需要使用这类工具的时候，不是自己执行构建，而是委派出去使用其他的agent来完成这个任务。其他agent完成这样的一个任务，给出确定的结果（比如：工具已经在 .roo/tools/ 下构建好了，如何如何使用），然后主agent只需要使用这个结果即可。然后可以运行这个工具。

---

For example：

1. 主模型： 我需要一个cli工具用于快速截图 build-tool --name screenshot-cli --type cli --params ...
2. 子模型： 好的，我已经帮你构建好了这个工具，路径是 .root/tools/screenshot-cli 你可以这样使用它 ...
3. 主模型： 好的，我现在使用这个工具来进行截图 ...
4. 主模型： 好的，截图完成，文件保存在，让我对其进行读取 ...
5. 主模型： 好的，我已经读取到了截图文件，接下来我需要对其进行分析 ...
6. 主模型： 这里有问题，让我进行修正 ...
7. 主模型： 好的，现在让我再次使用这个工具来进行截图 ...、

## 具体实现

给模型提供一个新的工具，该工具调用一个新的类型的 agent，这个 agent 专门用于构建工具。该 agent 可以根据主模型的需求，构建出相应的工具，并将工具的使用方法返回给主模型。

---

## 设计讨论记录

### 关于触发时机

**问题**：模型往往不会意识到它们需要这个工具。

**解决思路**：对主模型来说，调用 `build-tool` 的成本 ≈ 一次工具调用，而自己构建需要多步 CLI + 调试 + 验证。这样触发的门槛就变得很低——只要预期会用 2 次以上，就值得构建。

**动态参数增强复用**：工具应支持动态参数（如截图分辨率、裁切位置等），让"构建一次，多场景使用"成为可能。

### 关于构建成本

**子 agent 成本较低的原因**：

1. 子 agent 无需理解项目上下文，只需要构建一个独立的 CLI 工具
2. 任务边界明确，不涉及复杂的端到端逻辑

**缓存机制设计**：

- 两级缓存：全局目录（跨项目通用）+ 项目目录（项目特定）
- 下次构建时，先向子 agent 提供已有工具信息
- 子 agent 优先验证已有工具是否可用，避免重复构建

### 关于质量保证

**成本由子 agent 承担**：

- 子 agent 任务边界明确：构建 + 测试 + 返回使用说明
- 测试验证在子 agent 内完成，确保工具可用后再返回
- 主 agent 只需信任返回的结果，专注于使用工具解决问题

### 核心价值总结

```
主 agent 的认知负担 → 转移为 → 子 agent 的明确任务
复杂的多步骤操作 → 简化为 → 一次工具调用 + 后续复用
```

### 实现优先级建议

1. **基础框架**：`build-tool` 调用子 agent，返回工具路径和使用说明
2. **缓存机制**：全局/项目两级，避免重复构建
3. **工具发现**：让主 agent 能查询"已有哪些工具可用"

## 接口设计（2026-02-02 讨论确定）

### 设计原则

**主 agent 只描述"需要什么能力"，子 agent 决定"如何实现"**

主 agent 不应该负担：

- 技术选型（bash/python/node/...）
- 实现方式（cli/script/函数）
- 缓存位置（global/project）
- 参数设计

### 主 agent → 子 agent（输入）

使用结构化需求作为功能基线：

```json
{
	"requirement": "截取指定窗口的截图",
	"inputHint": "窗口名称、可选的裁切区域",
	"outputHint": "图片文件路径"
}
```

| 字段        | 必选 | 说明                    |
| ----------- | ---- | ----------------------- |
| requirement | ✅   | 工具需要实现的功能描述  |
| inputHint   | ❌   | 期望的输入格式/类型提示 |
| outputHint  | ❌   | 期望的输出格式/类型提示 |

### 子 agent → 主 agent（输出）

使用 `attempt_completion` 返回，包含三部分：

````
工具已构建完成！

**路径**: /path/to/tool

**使用说明** (`--help` 输出):
```
Usage: screenshot-cli [options]

Options:
  --window <name>     Window name to capture
  --region <x,y,w,h>  Optional region to crop
  --output <path>     Output file path
  --help              Show this help
```

**示例**:
```bash
screenshot-cli --window "Safari" --output ./screenshot.png
screenshot-cli --window "Safari" --region 0,0,800,600 --output ./cropped.png
```
````

### 子 agent 的职责

1. **技术选型**：根据需求选择最合适的实现方式
2. **参数设计**：设计合理的 CLI 参数
3. **缓存决策**：决定工具存放位置（全局/项目）
4. **质量保证**：实现 `--help`、错误处理、测试验证
5. **文档生成**：生成使用说明和示例

### ⚠️ 关键：默认限制

**为什么需要默认限制？**

模型的上下文窗口有限。如果工具输出过大（大图片、长文本），会导致上下文爆炸。主 agent 调用工具时可能忘记传递限制参数。

**文本输出限制：**

- 默认最多 2000 字符输出到 stdout
- 如果超过，截断并标记：`[TRUNCATED, full output: /path/to/file]`
- 完整结果写入文件，供后续检查

**图片输出限制：**

- 默认尺寸 800x600（更小，适合快速预览）
- 支持 `--focus x,y`：聚焦位置（0-1 归一化坐标），用于渐进式探索大图
- 支持 `--scale factor`：缩放因子，用于放大查看细节

**设计原则**：

- 默认输出适合模型处理
- 支持渐进式、按需探索（而不是一次性加载全部）
- 完整数据始终可访问（通过文件）

## 实现细节

### 专用模式

创建了 `tool-builder` 模式（而不是复用 `code` 模式），因为：

- `code` 模式已被 `apply_edit` 使用
- 工具构建有独特的职责和交付物要求
- 专用模式可以有针对性的 `customInstructions`

### 自动允许

`build_tool` 被添加到 `alwaysAllowSubtasks` 控制的工具列表中（与 `search_project`、`apply_edit`、`consult_expert` 一致），用户可以在设置中启用自动允许。

### 工具分组

`build_tool` 属于 `modes` 工具组（因为它本质上是 agent 派发），与其他 agent-as-tools 工具一致。

## Agent as Tool 原则应用（2026-02-02 更新）

### 工具描述优化

遵循 "Agent as Tool" 原则，工具描述中不应出现 "代理"、"agent"、"delegate" 等语义。模型应将其视为一个普通的、好用的工具，获得确定的输出结果。

**修改前**：

```
Delegates to a specialized agent that handles all implementation decisions.
What Sub-agent Decides (you don't need to think about):
```

**修改后**：

```
Handles all implementation decisions automatically.
What Gets Handled Automatically (you don't need to think about):
```

### 输出限制强调

在派发任务时，通过 `<output_limits>` XML 块再次强调输出限制要求：

```xml
<output_limits>
CRITICAL: Built tools MUST enforce these default output limits:
- Text: max 2000 chars to stdout. If exceeded, truncate with '[TRUNCATED, full output: /path/to/file]' and write complete result to file.
- Images: default 800x600. Support --focus x,y (0-1 normalized coords) for progressive exploration, and --scale factor for zoom.
These limits prevent context overflow when the tool is used repeatedly.
</output_limits>
```

这确保了：

1. 子任务明确知道输出限制的重要性
2. 构建的工具默认就支持这些限制
3. 主模型使用工具时不会因输出过大而导致上下文溢出
