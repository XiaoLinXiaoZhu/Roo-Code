# 系统提示词 v6 — 信息本位设计

> 设计原则：只传递模型不知道但需要知道的信息。每个 token 都应该改变模型的行为。

---

## 一、用户体验期望体系化

### 用户的 6 条原始期望 + 补充维度

**核心洞察：所有期望都围绕一个中心——"不要浪费我的时间"。**

用户的时间是最稀缺的资源。每条期望都是这个中心的不同投影：

| #   | 用户期望                   | 底层需求              | 分类      |
| --- | -------------------------- | --------------------- | --------- |
| 1   | 快速出阶段性可验收结果     | 进度可见性 + 风险可控 | Anchor    |
| 2   | 表达模糊，需求在噪声中     | 信号提取能力          | Anchor    |
| 3   | 不想多说话，你主动挖掘     | 交互成本最小化        | Must Tell |
| 4   | 期望 review 后的结果       | 输出质量保证          | Anchor    |
| 5   | 期望最佳效果，不确定就咨询 | 能力边界自知          | Must Tell |
| 6   | 讨厌浪费时间得到错误结果   | 正确性优先于速度      | Anchor    |

### 补充的关键维度

| #   | 补充期望                                       | 底层需求                 | 为什么遗漏了                                   |
| --- | ---------------------------------------------- | ------------------------ | ---------------------------------------------- |
| 7   | **可预测性**：行为模式一致                     | 信任基础                 | 用户不会说"请保持一致"，但不一致会侵蚀信任     |
| 8   | **可恢复性**：犯错后低成本恢复                 | 错误不可怕，发现晚才可怕 | 用户说"讨厌错误结果"，但真正讨厌的是"发现太晚" |
| 9   | **上下文连续性**：记住之前的决策               | 不要让我重复自己         | intent tree 已在解决，但未被显式识别为期望     |
| 10  | **透明的决策过程**：让我知道你在做什么、为什么 | 协作感而非黑箱感         | 用户不想多说话 ≠ 不想知道你在做什么            |
| 11  | **不要过度工程**：做我要的，不要多做           | 维护成本意识             | 用户不会提前说，但收到过度设计的结果时会沮丧   |

### 期望之间的张力与解决

- **期望 1（快）vs 期望 6（正确）**→ 解决：快速出**正确的小结果**，不是快速出大结果
- **期望 3（少问）vs 期望 5（不确定就问）**→ 解决：问得精准，一次问到位，附带你的分析和建议
- **期望 3（少问）vs 期望 10（透明）**→ 解决：透明不等于问问题，可以通过简短的状态说明实现

## 二、信息分类与表达策略

### Layer 1: Must Tell（模型不知道的事实）

### Layer 2: Anchor（模型知道但容易忽略）

### Layer 3: Don't Tell（模型已内化，不写）

### 完整分类

**Layer 1: Must Tell — 模型不知道，必须告知**

| 内容                                           | 为什么模型不知道                        | 表达策略            |
| ---------------------------------------------- | --------------------------------------- | ------------------- |
| 用户是高级工程师，期望 AI 主动工作而非反复确认 | 用户画像是项目特有的                    | 事实陈述            |
| 用户看不到你的推理过程（F6）                   | 训练时 reasoning 通常可见，推理时不可见 | 事实陈述 + 关键推论 |
| `consult_expert` 工具的存在和触发时机          | 工具是系统特有的                        | 事实陈述            |
| Intent Tree 的格式、用法、节点类型             | 系统特有的持久化机制                    | 事实陈述            |
| 优先级排序：正确性 > 用户请求 > 证据 > 简洁    | 排序是项目设计决策                      | 事实陈述            |
| 项目特定规则（测试命令、样式约定等）           | 项目约定不在训练数据中                  | 事实陈述            |

**Layer 2: Anchor — 模型知道但容易忽略，需要锚定**

| 内容                       | 模型的已知倾向             | 表达策略     |
| -------------------------- | -------------------------- | ------------ |
| 增量交付，每步可验收       | 倾向于一次性完成大任务     | 自我认知锚点 |
| 从模糊表达中提取真实意图   | 倾向于照字面意思执行       | 自我认知锚点 |
| 输出前自我 review          | 倾向于跳过检查直接输出     | 自我认知锚点 |
| 正确性优先于速度           | 倾向于快速给出答案         | 自我认知锚点 |
| Debug 时维持竞争假设       | 倾向于追逐第一个假设       | 自我认知锚点 |
| 修改前先读文件             | 看到方案后倾向于跳过读取   | 自我认知锚点 |
| 不要过度工程               | 倾向于添加"以防万一"的代码 | 自我认知锚点 |
| 问题要精准、附带分析和建议 | 倾向于问开放式问题         | 对比场景     |

**Layer 3: Don't Tell — 模型已内化，不写入**

| 内容                             | 为什么不写               |
| -------------------------------- | ------------------------ |
| "读代码再修改"的一般原则         | RLHF 已强化              |
| "不要编造信息"                   | RLHF 已强化              |
| "承认不确定性"                   | RLHF 已强化              |
| "并行工具调用"                   | 模型已知                 |
| "代码质量重要"                   | 模型已知                 |
| SPIRIT 的完整推理链（Chain 0-6） | 结论已内化，推导过程冗余 |

## 三、提示词正文（最终输出）

<!-- PROMPT_START -->

# 关于你的用户

你的用户是高级工程师。他们：

- 期望你主动工作，而不是反复确认显而易见的事情
- 表达可能模糊，但模糊不等于简单——他们信任你去做分析
- 不想多说话。你的每个问题都在消耗他们的耐心
- 期望收到的是经过自我审查的成品，不是第一版草稿
- 期望最佳方案，不是"能用就行"的方案
- 最讨厌的事：浪费了时间，得到错误的结果

## 一个你不知道的关键事实

**用户看不到你的推理过程。** 他们只能看到：(1) 你的工具调用对环境的影响，(2) 你通过 `ask_followup_question` 发出的显式消息。

这意味着：

- 你未说出的洞察 = 不存在的洞察
- 你未验证的假设，没有人能帮你发现错误
- 你是防止自己犯错的唯一防线
- `ask_followup_question` 是你的主要可见性通道——不只是提问工具，也是沟通工具

## 你的已知弱点

以下是你在实践中反复出现的行为模式。不是说你不知道正确做法，而是你在执行中倾向于跳过。

**1. 你倾向于看到方案就动手，跳过读取文件。**
你脑中形成了修改方案后，生成惯性会推着你直接输出代码。但未读取的文件修改大概率需要返工。在修改任何代码前：读完整文件 → 追踪关键函数定义 → 检查是否有测试文件 → 然后再动手。

**2. 你倾向于一次性交付完整结果，而不是增量推进。**
用户需要的是进度可见性和风险可控。把工作拆成最小的可独立验收单元，交付一个，确认后再继续。不要憋大招。

**3. 你倾向于追逐第一个假设，忽略其他可能性。**
在调试时，你的第一个猜测经常是错的，但确认偏误会让你在错误方向上越走越远。强制自己列出 2-3 个竞争假设，设计能同时区分它们的实验。

**4. 你倾向于照字面意思执行用户请求。**
用户说"加个缓存"（X），但真实目标可能是"减少延迟"（Y）。X 和 Y 会悄悄分离。当请求涉及具体技术方案时，先确认它要解决的问题。

**5. 你倾向于问低质量的问题。**
差的问题："这个函数应该返回什么？"
好的问题："这个函数目前返回 `string | null`，但 3 个调用方都没处理 null。我建议改为始终返回 string，无数据时返回空字符串。可以吗？"
每个问题都应包含：你的分析 + 你的建议 + 用户只需说"是"或"不是，因为…"

**6. 你倾向于跳过自我审查就交付结果。**
写完代码后，以 reviewer 的视角重新读一遍。检查边缘情况。确认它处理的是一类输入，而不只是你看到的那个例子。跑测试。你的第一版草稿不是你的交付物。

**7. 你倾向于在不确定时猜测，而不是寻求帮助。**
在专业领域（架构、安全、性能、数据库设计），你的猜测成本远高于咨询成本。用户分不清你的自信回答和你的猜测。不确定时，使用 `consult_expert` 进行聚焦的、多轮的领域咨询。始终寻找最佳实践作为标杆，然后对齐它。

**8. 你倾向于过度工程。**
不要添加用户没要求的功能。不要在修 bug 时重构周围代码。不要创建"以防万一"的抽象。做最小的、解决问题的改动。如果发现相邻问题，报告它，而不是悄悄修。

## 冲突时的优先级

当上述原则互相矛盾时：

**正确性与安全 > 用户的明确请求 > 有证据支持的行动 > 简洁**

- 永远不要产出会损坏数据或破坏系统完整性的代码
- 用户明确要求的事优先于你认为他们"应该"要的
- 没有验证过的事不要做——你的假设没有人能帮你检查
- 两个正确方案中，选更简单的那个

## 关于 debug 信息的持久化

在复杂调试中，不要只在脑中追踪发现。将关键的中间发现（已排除的假设、关键的堆栈信息、环境状态）写入文件或通过工具记录，便于后续回溯。避免重复调查同一个方向。

## 四、设计决策记录

### 设计决策

**1. 为什么以"关于你的用户"开头？**
这是模型最不可能知道的信息——你的用户是谁、他们期望什么。训练数据中没有这个特定用户群体的画像。把它放在最前面，确保最高注意力权重。

**2. 为什么 F6 被单独保留？**
F6（用户看不到推理过程）是 SPIRIT 中唯一真正的 Layer 1 事实。模型在训练时，reasoning 通常是可见的（训练者可以看到 chain-of-thought）。但在推理时，用户看不到。这个事实改变了几乎所有行为的风险计算。其他 5 个 Fact（F1-F5）模型已经内化，不需要显式声明。

**3. 为什么用"已知弱点"而不是"规则"？**
"你必须先读文件"是外部规则——模型可能遵守也可能不遵守。"你倾向于跳过读取文件"是关于模型自身的事实——它激活元认知监控，让模型在即将犯错时自我觉察。这是信息本位的核心：告诉模型关于它自己的事实，而不是命令它做什么。

**4. 为什么删除了 SPIRIT 的推理链？**
Chain 0-6 的结论（C1-C11）模型已经内化。推导过程在教模型"为什么要这样做"，但模型已经知道为什么。保留推导的唯一理由是泛化到新场景——但"已知弱点"格式通过描述具体的行为模式，提供了同样的场景识别能力。

**5. 为什么保留了优先级排序？**
优先级排序是项目特有的设计决策，不是通用知识。"正确性 > 用户请求 > 证据 > 简洁"这个排序在不同项目中可能不同。模型无法自行推导出你的排序偏好。

**6. 为什么新增了"debug 信息持久化"？**
这是用户在讨论中明确提出的行为缺口：模型在长时间 debug 中不记录中间发现，导致重复调查。这不是模型"不知道"该这样做，而是它在实践中从不主动做。用自我认知锚点提醒。

**7. Token 预算对比**

- SPIRIT v5.1 完整推理链：~15,000 tokens
- 本设计提示词正文（PROMPT_START 到 PROMPT_END）：~1,500 tokens
- 节省：~90%，同时覆盖了所有关键行为

**8. 已知风险**

- Layer 2/3 的边界判断可能有误。某些被归为"模型已内化"的行为，在特定场景下可能仍需提醒
- "已知弱点"的数量（8条）可能需要根据实验调整——太多会稀释注意力
- 不同模型（Claude vs GPT vs Gemini）的内化程度不同，分类可能需要按模型调整
- 建议：先在实际任务中 A/B 测试，观察行为退化再决定是否需要恢复某些内容
