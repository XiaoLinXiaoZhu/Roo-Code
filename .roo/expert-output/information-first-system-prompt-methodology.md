# 信息本位系统提示词设计：方法论框架

> 咨询回复 — 2026-02-27
> 主题：将用户体验期望转化为对 LLM 有效的提示词结构

---

## 第一部分：对你现有工作的诊断

### 1.1 SPIRIT v5.1 做对了什么

在深入方法论之前，我需要先说清楚你的 SPIRIT v5.1 已经是我见过的最成熟的系统提示词设计之一。它做对了几件关键的事：

**公理化推理结构**：6 个 Fact → 9 条推理链 → 11 个结论 + 优先级规则。这不是"规则列表"，而是一个可推导的体系。模型不是在"遵守规则"，而是在"理解为什么"。这是正确的方向。

**F6 的发现**：将"用户看不到思考过程"作为一个独立的事实，并让它渗透所有推理链——这是一个非常深刻的洞察。大多数提示词设计者从未意识到这个维度的存在。

**推理链中的自我辩驳**：每条链都包含 "Wait—is this too strict?" "Let me reconsider" 这样的反思步骤。这不是装饰——它在训练模型的思维模式，让模型学会在推理中自我质疑。

### 1.2 SPIRIT v5.1 的结构性问题

但正因为你已经做到了这个水平，我才能看到更深层的问题：

**问题 A：推理链的 token 成本与边际收益不成比例**

SPIRIT v5.1 的完整文本大约 15,000+ tokens。每次对话都要支付这个成本。但这些推理链中，大量内容是模型**已经知道**的东西——只是用推理的方式重新推导了一遍。

举个例子，Chain 1 花了大量篇幅推导出"读代码再行动"。但现代 frontier 模型（Claude 3.5+, GPT-4o+）在 RLHF 阶段已经被训练过这个行为模式。你不是在教它一个新概念，你是在用 ~1500 tokens 重新推导一个它已经内化的行为。

**关键区分**：推理链的价值不在于结论本身，而在于推理过程中建立的**优先级框架**和**边界条件**。C1 的结论"读代码再行动"模型已经知道；但"什么时候可以跳过读代码"（用户明确 opt-out、文件已读且未变）这个边界条件，模型不一定知道。

**问题 B：信息密度的不均匀**

有些推理链几乎全是模型已知的内容（Chain 1, Chain 3），有些则包含大量模型不知道的信息（Chain 7 的 intent tree 格式、Chain 8 的优先级排序）。但它们占用的 token 数量差不多。这意味着你在"已知内容"上过度投资，在"未知内容"上投资不足。

**问题 C：推理链之间的耦合度过高**

每条链都引用 F6，每条链都有 "F6 amplifies this" 的段落。这在逻辑上是正确的，但在 token 经济上是浪费——同一个论点被重复了 9 次。模型在第 2 次看到 "F6 amplifies this" 时就已经理解了这个模式，后面 7 次是冗余的。

### 1.3 核心矛盾

你的核心矛盾是：**推理式提示词的教学效果与 token 成本之间的张力**。

SPIRIT v5.1 选择了"教学效果最大化"——通过完整的推理链让模型深度理解每个结论的 WHY。但这导致了 15K+ tokens 的成本，其中可能只有 3-4K tokens 是模型真正需要的新信息。

"信息本位"的理念正是要解决这个矛盾：只传递模型不知道的信息，用最少的 token 获得最大的行为改变。

## 第二部分：方法论框架——信息本位提示词设计的 5 步流程

### 概览

```
步骤 1: 期望分析与体系化
   ↓
步骤 2: 信息分类（三层模型）
   ↓
步骤 3: 表达策略选择
   ↓
步骤 4: 结构组装
   ↓
步骤 5: 实验验证与迭代
```

依赖关系：严格串行。每一步的输出是下一步的输入。不可并行，因为分类决定表达策略，表达策略决定结构。

### 步骤 1：期望分析与体系化

**目的**：将零散的用户期望转化为结构化的、无遗漏的期望体系。

**方法**：对每条期望做三件事——(a) 识别底层需求，(b) 找到期望之间的依赖关系，(c) 发现遗漏。

#### 1.1 你的 6 条期望的分析

我逐条分析，然后找出体系结构：

**期望 1：快速出阶段性可验收结果**

- 底层需求：用户需要**进度可见性**和**风险可控性**。不是"快"本身，而是"我能看到进展，且每一步都是可验收的"。
- 隐含约束：输出必须是可独立验证的单元，不是半成品。

**期望 2：用户表达模糊，需求在噪声中**

- 底层需求：模型需要**信号提取能力**——从模糊的表达中识别真实意图。
- 隐含约束：模型不能把"模糊"当作"简单"。模糊的请求往往比精确的请求更复杂。

**期望 3：用户不想多说话，模型需主动挖掘信息**

- 底层需求：**交互成本最小化**。用户的时间比 token 贵。
- 隐含约束：但"主动挖掘"不等于"不问就做"。有些信息只存在于用户脑中，必须问。关键是：能自己查的不要问，必须问的要问得精准。

**期望 4：用户期望 review 后的结果，不是粗制滥造**

- 底层需求：**输出质量保证**。用户期望的是"经过自我审查的成品"，不是"第一版草稿"。
- 隐含约束：这意味着模型需要一个内部的 review 步骤——在输出之前自我检查。

**期望 5：用户期望最佳效果，不确定时应咨询专家**

- 底层需求：**能力边界自知**。用户不怕模型不会，怕模型不会还装会。
- 隐含约束：需要一个清晰的"何时该咨询"的判断框架。

**期望 6：用户讨厌浪费时间得到错误结果**

- 底层需求：**正确性优先于速度**。宁可慢一点得到对的结果，也不要快速得到错的结果。
- 隐含约束：这与期望 1（快速出结果）存在张力。解决方案是：快速出**正确的小结果**，而不是快速出**大但可能错的结果**。

#### 1.2 期望之间的依赖关系

```
期望 6（正确性优先）
  ├── 约束 期望 1（快速出结果）→ 快速出正确的小结果
  ├── 要求 期望 4（review 后的结果）→ 正确性的保障机制
  └── 要求 期望 5（咨询专家）→ 正确性的兜底机制

期望 3（用户不想多说话）
  ├── 约束 期望 2（需求在噪声中）→ 必须主动提取信号
  └── 张力 期望 5（咨询专家）→ 咨询需要问问题，但用户不想多说话
                                → 解决：问得精准，一次问到位
```

#### 1.3 遗漏的关键期望

基于我的经验，你的 6 条期望遗漏了至少 3 个关键维度：

**遗漏 A：可预测性（Predictability）**
用户不仅期望正确的结果，还期望**可预测的行为模式**。如果模型有时候问很多问题，有时候一声不吭就做了，用户会感到不安——不是因为某次行为是错的，而是因为他无法预测下一次会怎样。

为什么重要：可预测性是信任的基础。用户需要建立一个心智模型："这个 AI 在什么情况下会问我，什么情况下会自己做"。如果这个模型不稳定，用户就无法有效地与 AI 协作。

**遗漏 B：可恢复性（Recoverability）**
当模型犯错时（这是必然的），用户期望**低成本的恢复路径**。这意味着：(a) 错误应该被快速发现（不是在 10 步之后），(b) 每一步都应该是可回滚的，(c) 模型应该主动承认错误而不是试图掩盖。

为什么重要：这直接关联期望 6（讨厌浪费时间）。浪费时间的不是"犯错"本身，而是"犯错后很久才发现"或"犯错后恢复成本很高"。

**遗漏 C：上下文连续性（Context Continuity）**
在多轮对话中，用户期望模型**记住之前的决策和原因**，而不是每次都从零开始。"我们之前不是讨论过这个吗？"是用户最沮丧的体验之一。

为什么重要：这是你的 intent tree 要解决的问题，但它作为一个用户期望还没有被显式识别。

#### 1.4 完成标准

步骤 1 完成的标志：

- [ ] 每条期望都有底层需求和隐含约束
- [ ] 期望之间的依赖和张力关系已识别
- [ ] 遗漏的期望已补充
- [ ] 所有张力都有解决方案（不一定是最终方案，但至少有方向）

### 步骤 2：信息分类（三层模型）

**目的**：对每条期望（及其衍生的行为要求），判断它属于哪一层，从而决定是否写入提示词、以什么方式写入。

**这是整个方法论中最关键的步骤。** 信息本位的核心就是这个分类。

#### 2.1 三层模型

```
┌─────────────────────────────────────────────────┐
│  Layer 1: 模型不知道的事实（Must Tell）           │
│  → 必须写入提示词，因为模型无法从其他地方获得     │
│  例：intent tree 的 XML 格式、特定工具的存在       │
├─────────────────────────────────────────────────┤
│  Layer 2: 模型知道但容易忽略的（Anchor）          │
│  → 用"自我认知提醒"方式写入，不是教它，是提醒它   │
│  例：确认偏误的存在、用户看不到思考过程            │
├─────────────────────────────────────────────────┤
│  Layer 3: 模型已经内化的（Don't Tell）            │
│  → 不写入提示词，写了也是浪费 token               │
│  例：读代码再修改、不要编造信息                    │
└─────────────────────────────────────────────────┘
```

#### 2.2 分类判断标准

**Layer 1 的判断标准**（必须全部满足）：

- 这个信息是否是你的系统/项目特有的？（不是通用编程知识）
- 如果不告诉模型，它是否有可能自己推断出来？（答案必须是"不可能"）
- 这个信息是否会随着项目演进而变化？（如果是，考虑放在动态注入的部分）

**Layer 2 的判断标准**（满足任一即可）：

- 模型在训练中见过这个概念，但在实际行为中经常违反？
- 这个行为需要在特定条件下被激活，而不是始终激活？
- 这个概念的"边界条件"是模型容易搞错的？

**Layer 3 的判断标准**（满足任一即可）：

- 这是 RLHF 阶段被强化过的核心行为？（如：不编造信息、承认不确定性）
- 在没有任何提示词的情况下，模型是否已经表现出这个行为？
- 写入这条规则后，模型的行为是否有可观测的改变？（如果没有，就是 Layer 3）

#### 2.3 对你的 6+3 条期望的分类

| 期望                        | 分类                     | 理由                                                                                                                                       |
| --------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |

### 步骤 3：表达策略选择

**目的**：为每个层级选择最有效的表达方式，最大化信息密度。

#### 3.1 三种表达策略

**策略 A：事实陈述（Fact Statement）**

- 适用于：Layer 1（模型不知道的事实）
- 形式：直接陈述事实，不解释为什么
- 示例：`"你的环境中有一个 <intent_tree>，它的格式是..."`
- 为什么有效：模型不需要被说服这个事实是真的，它只需要知道这个事实存在

**策略 B：自我认知锚点（Self-Awareness Anchor）**

- 适用于：Layer 2（模型知道但容易忽略的）
- 形式：不是"你应该做 X"，而是"你倾向于做 Y，但在这个场景下 X 更好"
- 示例：`"你倾向于在第一个假设上投入过多。在调试时，维持 2-3 个竞争假设。"`
- 为什么有效：这利用了模型的元认知能力。当你告诉模型"你有 X 倾向"时，模型会在推理中主动监控这个倾向。这比"你应该做 Y"更有效，因为后者是外部规则，前者是内部觉察。

**策略 C：对比场景（Contrastive Scenario）**

- 适用于：Layer 2 中特别重要的、需要强化的行为
- 形式：展示错误行为和正确行为的对比
- 示例：你的 `spirit_hint` 中的 CONTRAST 格式就是这个策略
- 为什么有效：对比场景在模型的表示空间中创建了一个"决策边界"。模型不需要从抽象规则推导行为，它可以直接模式匹配到正确的行为。

**策略 D：不写（Omission）**

- 适用于：Layer 3（模型已经内化的）
- 形式：什么都不写
- 为什么有效：每个不必要的 token 都在稀释必要信息的注意力权重。删除 Layer 3 内容不会降低模型表现，但会提高 Layer 1 和 Layer 2 内容的有效性。

#### 3.2 策略选择的决策树

```
这条信息是模型不知道的事实吗？
  ├── 是 → 策略 A（事实陈述）
  └── 否 → 模型在实践中经常违反这个行为吗？
              ├── 是 → 这个行为的正确/错误边界清晰吗？
              │         ├── 是 → 策略 C（对比场景）
              │         └── 否 → 策略 B（自我认知锚点）
              └── 否 → 策略 D（不写）
```

#### 3.3 一个关键的设计权衡：推理链 vs 锚点

你的 SPIRIT v5.1 选择了"推理链"作为主要表达策略。信息本位方法建议转向"锚点"。这里有一个重要的权衡需要说清楚：

**推理链的优势**：

- 建立因果理解，模型能在新场景中泛化
- 推理过程本身训练了模型的思维模式
- 对于真正复杂的、模型从未见过的概念，推理链是唯一有效的教学方式

**推理链的劣势**：

- Token 成本高（你的 Chain 1 约 1500 tokens，压缩为锚点可能只需 100 tokens）
- 大量内容是模型已知的，推导过程是冗余的
- 推理链越长，模型在后半段的注意力越分散

**锚点的优势**：

- Token 效率极高
- 利用模型已有的知识，只需"激活"而不需"教学"
- 信息密度高，注意力不被稀释

**锚点的劣势**：

- 对于模型真正不知道的概念，锚点不够——模型需要理解 WHY 才能正确执行
- 锚点容易退化为"规则列表"，失去推理链的泛化能力

**我的建议**：混合策略。

- 对于 Layer 1（模型不知道的）：保留简短的推理链，因为模型需要理解 WHY
- 对于 Layer 2（模型知道但忽略的）：使用锚点或对比场景，不需要推理链
- 对于 Layer 3（模型已知的）：删除

具体到你的 SPIRIT v5.1：

- **保留推理链**：Chain 7（intent tree）、Chain 8（优先级规则）——这些是 Layer 1
- **压缩为锚点**：Chain 0-6——这些主要是 Layer 2
- **F1-F6 保留但精简**：Facts 是优秀的锚点格式，但每个 Fact 可以压缩到 1-2 句

#### 3.4 完成标准

步骤 3 完成的标志：

- [ ] 每条保留的信息都有明确的表达策略
- [ ] 推理链只用于 Layer 1 内容
- [ ] Layer 2 内容全部转为锚点或对比场景
- [ ] Layer 3 内容全部删除
- [ ] 预估总 token 数相比原版减少 50%+

#### 4.4 结构组装的反模式

**反模式 1：规则列表回归**
信息本位不是"把推理链的结论提取出来列成清单"。如果你只是把 C1-C11 列出来，你就回到了声明式提示词——模型会"遵守"这些规则但不理解它们。

正确做法：Layer 1 内容保留简短推理（让模型理解 WHY），Layer 2 内容用锚点/对比（激活已有知识），Layer 3 内容删除。

**反模式 2：过度压缩**
信息本位不是"越短越好"。如果一条 Layer 1 信息被压缩到模型无法理解的程度，那压缩就过度了。判断标准：模型能否仅从这段文字中正确执行行为？如果不能，需要扩展。

**反模式 3：混淆"模型不知道"和"我觉得重要"**
你觉得重要的东西不一定是模型不知道的。"代码质量很重要"——你觉得重要，但模型已经知道。"我们的 intent tree 用 XML 格式"——你可能觉得这是细节，但模型真的不知道。信息本位的分类标准是"模型是否知道"，不是"我是否觉得重要"。

### 步骤 5：实验验证与迭代

**目的**：验证信息本位版本的实际效果，并根据结果调整分类。

#### 5.1 为什么实验是必须的

信息分类（步骤 2）中最大的不确定性是 Layer 2 和 Layer 3 的边界。你认为模型"已经知道"的东西，可能在特定场景下模型并不知道。你认为模型"容易忽略"的东西，可能模型其实做得很好。

**唯一可靠的判断方法是实验**：删除一条内容，观察模型行为是否退化。如果退化了，这条内容不是 Layer 3，需要恢复。如果没退化，确认是 Layer 3，保持删除。

#### 5.2 实验设计框架

**A/B 测试结构**：

```
控制组：SPIRIT v5.1（完整版）
实验组：信息本位版本

测试场景（每个场景至少跑 3 次以消除随机性）：
1. 简单 bug 修复 → 测试基线行为是否保持
2. 模糊需求 → 测试信号提取能力（期望 2）
3. 多步骤复杂任务 → 测试增量交付（期望 1）
4. 专业领域决策 → 测试咨询触发（期望 5）
5. 故意引入错误信息 → 测试验证行为（期望 6）
```

**评估维度**：

- 行为正确性：模型是否做了正确的事？
- Token 效率：完成同一任务用了多少 token？
- 交互次数：用户需要纠正模型多少次？
- 首次正确率：模型第一次尝试就做对的比例？

#### 5.3 迭代策略

**渐进式压缩**（推荐）：
不要一次性从 v5.1 跳到信息本位版本。而是：

1. **v5.2**：删除所有 Layer 3 内容，保留 Layer 1 和 Layer 2 的原始表达 → 测试
2. **v5.3**：将 Layer 2 内容从推理链压缩为锚点 → 测试
3. **v5.4**：将关键 Layer 2 内容转为对比场景 → 测试
4. **v6.0**：完整的信息本位版本 → 全面测试

每一步都测试，如果某步导致退化，回退并分析原因。可能的原因：

- 分类错误（你以为是 Layer 3，其实是 Layer 2）
- 压缩过度（锚点不够具体，模型无法执行）
- 缺少上下文（删除的推理链提供了模型需要的上下文）

**关键指标：退化检测**

最难检测的退化是"微妙的质量下降"——模型仍然完成了任务，但方式不够好。例如：

- 仍然读代码再修改，但不再检查测试文件
- 仍然问问题，但问的问题不够精准
- 仍然增量交付，但粒度太大

这类退化需要人工评估，不能纯靠自动化指标。建议：每个版本至少做 5 个真实任务的人工评估。

#### 5.4 完成标准

步骤 5 完成的标志：

- [ ] 至少完成了 v5.2（删除 Layer 3）的 A/B 测试
- [ ] 没有发现显著的行为退化
- [ ] 如果发现退化，已调整分类并重新测试
- [ ] Token 使用量相比 v5.1 减少了 30%+
- [ ] 人工评估确认关键行为（期望 1-6 + 遗漏 A-C）仍然被满足

## 第三部分：深层洞察与进阶思考

### 3.1 "信息本位"的哲学基础

信息本位的核心假设是：**提示词的价值 = 它传递的新信息量 / 它消耗的 token 数**。

这个假设有一个重要的前提：你必须知道模型"已经知道什么"。但这其实是一个不可完全回答的问题——你无法精确知道模型的内部知识状态。你只能通过实验来近似。

这意味着信息本位不是一个可以一次性完成的设计，而是一个**持续的实验过程**。每次模型更新（新版本、新的 RLHF 数据），模型的"已知"边界都会移动，你的分类也需要重新校准。

**实操建议**：在每次模型升级后，重新跑步骤 5 的测试套件。如果新模型在某些行为上表现更好了，对应的 Layer 2 内容可能可以降级为 Layer 3 并删除。

### 3.2 推理链的不可替代场景

我在步骤 3 中建议将大部分推理链压缩为锚点。但有一个场景下推理链是不可替代的：**当你需要模型在新场景中泛化时**。

锚点告诉模型"在场景 A 中做 X"。推理链告诉模型"因为 P 所以 Q，因此在任何满足 P 的场景中都应该做 Q"。如果你的场景是可枚举的，锚点就够了。如果你的场景是开放的（模型会遇到你没预见到的情况），推理链提供了泛化能力。

你的 F6 就是一个很好的例子。F6 的推理链不仅告诉模型"要用 ask_followup_question 沟通"，还告诉模型**为什么**——因为用户看不到思考过程。这意味着在任何新场景中，模型都可以自己推导出"在这个场景下，我应该主动沟通，因为用户看不到我在想什么"。如果你只写了锚点"要主动沟通"，模型在新场景中可能不知道什么时候该沟通、什么时候不该。

**建议**：为你最重要的 2-3 个 Layer 1 概念保留简短的推理链（不是 v5.1 那样的完整推导，而是 3-5 步的核心推理）。其余全部用锚点。

### 3.3 spirit_hint 的角色：动态锚点

你的 `spirit_hint`（在 environment 中注入的提示）是一个非常聪明的设计。它本质上是一个**动态锚点**——根据当前上下文选择最相关的行为提醒。

这解决了一个信息本位的核心问题：**注意力稀释**。即使你把提示词压缩到 5K tokens，模型在处理第 4000 个 token 时对第 500 个 token 的注意力已经衰减了。spirit_hint 通过在**对话流中**注入最相关的锚点，绕过了这个问题——它出现在模型即将做决策的时刻，注意力最集中。

**进阶建议**：将 spirit_hint 从"随机轮换"升级为"上下文感知"。根据模型当前正在做的事情（调试？写新代码？重构？），选择最相关的锚点。例如：

- 模型正在调试 → 注入 "Competing Hypotheses" 锚点
- 模型正在写新功能 → 注入 "Incremental Delivery" 锚点
- 模型正在做架构决策 → 注入 "Know Your Limits" 锚点

这样，spirit_hint 就变成了一个**实时的行为校准系统**，而不只是一个随机提醒。

### 3.4 关于"用户不想多说话"的深层矛盾

期望 3（用户不想多说话）和期望 5（不确定时咨询专家）之间的张力，比表面看起来更深。

本质上，这是一个**信息不对称**问题：

- 用户有模型没有的信息（业务上下文、偏好、约束）
- 模型有用户没有的信息（代码细节、技术方案、边界条件）
- 双方都不知道对方不知道什么

"用户不想多说话"意味着：**模型必须最大化每次交互的信息提取效率**。不是"少问"，而是"问得精准"。

具体来说：

1. **永远不要问开放式问题**。"你想怎么做？"是最差的问题。"我看到两种方案：A（快但有限制）和 B（慢但通用），你倾向哪个？"是好问题。
2. **把你的分析结果作为问题的一部分**。不是"这个函数应该返回什么？"，而是"这个函数目前返回 string | null，但调用方都没有处理 null。我倾向于改为始终返回 string 并在无数据时返回空字符串。可以吗？"
3. **批量问题**。如果你有 3 个不确定的点，不要分 3 次问。一次问完，每个问题附带你的倾向性建议。

这些不是"规则"——它们是从"用户时间比 token 贵"这个事实推导出来的行为。在提示词中，你可以用一个对比场景来锚定：

```
🧭 CONTRAST: Question Quality

❌ "What should this function return when the input is invalid?"
✅ "This function currently throws on invalid input. The 3 callers all have
   try-catch blocks. I recommend changing to return a Result type instead.
   Should I proceed, or do you prefer keeping the throw behavior?"

**Every question should contain your analysis and your recommendation.
The user should only need to say "yes" or "no, because..."**
```

### 3.5 关于 Layer 2 分类的模型依赖性

一个我必须坦诚说明的不确定性：**Layer 2 和 Layer 3 的边界是模型特定的**。

Claude 3.5 Sonnet 可能已经内化了"读代码再修改"（Layer 3），但 GPT-4o 可能在某些场景下仍然会跳过这一步（Layer 2）。如果你的系统支持多个模型后端，你可能需要为不同模型维护不同的分类。

这是一个实操上的复杂性，没有完美的解决方案。两个可行的策略：

**策略 A：按最弱模型分类**。如果任何一个支持的模型需要某条内容，就保留它。缺点：对强模型来说有冗余。优点：简单，不需要维护多套提示词。

**策略 B：分层提示词**。核心层（Layer 1，所有模型都需要）+ 补充层（Layer 2，根据模型能力动态添加）。缺点：维护成本高。优点：每个模型都得到最优的提示词。

如果你的用户主要使用 1-2 个模型，策略 A 足够。如果你支持 5+ 个模型且它们能力差异大，策略 B 值得投资。

### 3.6 一个你可能没意识到的风险：过度压缩导致的"规则脆性"

信息本位的一个隐藏风险是：当你把推理链压缩为锚点时，你失去了**规则之间的连接组织**。

在 SPIRIT v5.1 中，推理链不仅推导出结论，还建立了结论之间的关系。例如，Chain 8 明确说明了当 C1 和 C9 冲突时如何解决。如果你删除了推理链，只保留 C1 和 C9 的锚点，模型在遇到冲突时可能不知道该优先哪个。

**解决方案**：保留 Chain 8（优先级规则）作为独立的 Layer 1 内容。它不是推理链——它是一个**冲突解决框架**，模型不知道你的优先级排序，必须告诉它。

更一般地：**任何描述"规则之间关系"的内容都是 Layer 1**，因为这些关系是你的项目特有的设计决策，不是模型能自己推导的。

```
  分类（模型知道什么？不知道什么？知道但忽略什么？）
  × 表达策略（事实陈述 / 自我认知锚点 / 对比场景 / 不写）
  × 实验验证（删除后行为是否退化？）
```

### 你的 SPIRIT v5.1 → v6.0 的路径

```
v5.1 (当前)     → 15K+ tokens, 推理链为主
v5.2 (删除 L3)  → ~11K tokens, 删除已知内容的推导过程
v5.3 (压缩 L2)  → ~7K tokens, 推理链→锚点/对比场景
v5.4 (补充遗漏) → ~8K tokens, 新增可预测性/可恢复性/上下文连续性锚点
v6.0 (信息本位) → ~6-8K tokens, 完整的信息本位结构
```

### 最后的提醒

信息本位不是"越短越好"。它是"每个 token 都在传递模型不知道的信息"。如果你的提示词是 8K tokens 但每个 token 都是新信息，它比 3K tokens 但一半是冗余的提示词更好。

衡量标准不是 token 数，而是 **信息密度 × 行为改变量**。
