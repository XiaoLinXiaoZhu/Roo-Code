## 1. 核心问题诊断

### 为什么预估总是偏低？

你观察到的偏低预估不是偶然的，而是三个系统性偏差叠加的结果：

**偏差 1：Planning Fallacy（规划谬误）**

人类和 LLM 都有同样的认知偏差：预估时想的是"顺利路径"（happy path），而实际执行中总会遇到意外。这在 coding agent 场景下尤其严重，因为：

- 代码库的实际复杂度在读之前是未知的
- 类型传播、调用链深度、边界情况都是"读了才知道"的
- 每一个"意外发现"都会插入额外的调查轮次

**偏差 2：动作粒度错觉**

当你在脑中规划"读取代码结构"时，这感觉像一个动作。但在 agent 的执行模型中，它是 N 个动作——每个文件一轮。人类思维中的"一步"和 agent 执行中的"一轮"之间存在粒度不匹配。

关键洞察：**预估的单位必须是"工具调用次数"，而不是"概念步骤数"。**

**偏差 3：串行约束被低估**

即使 agent 支持并行工具调用，大多数编码任务的步骤之间存在数据依赖：

- 必须先读文件才能决定改什么
- 必须先改完才能跑测试
- 必须先看测试结果才能修 bug

并行能力只在少数场景有效（如同时读取多个独立文件），大部分工作是严格串行的。

### 核心结论

> **合理的预估 = 概念步骤数 × 每步的平均工具调用数 × 串行系数 + 意外缓冲**
>
> 而大多数人（和 LLM）只算了"概念步骤数"。

## 2. 第一性原理

### 轮次消耗的原子模型

一个 coding agent 的每一轮（1 assistant response）本质上是一个**原子操作**。理解轮次消耗的关键是把任务分解到原子操作级别。

**原子操作类型及其消耗：**

| 原子操作                | 轮次消耗 | 说明                       |
| ----------------------- | -------- | -------------------------- |
| 读取 1 个文件           | 1 轮     | 不可压缩                   |
| 编辑 1 个文件           | 1 轮     | 不可压缩                   |
| 执行 1 个命令           | 1 轮     | 不可压缩                   |
| 查找定义/引用           | 1 轮     | 不可压缩                   |
| 提问/沟通               | 1 轮     | 且用户响应后还需 1 轮处理  |
| 并行读取 N 个无依赖文件 | 1 轮     | 可压缩——但仅当文件间无依赖 |
| 并行执行 N 个无依赖工具 | 1 轮     | 同上                       |

**任务轮次 = Σ(各串行阶段的原子操作数)**

### 任务的通用执行阶段模型

几乎所有 coding 任务都遵循四阶段模型：

```
1.调查(读取理解) → 2.规划(设计方案) → 3.实施(编辑文件) → 4.验证(测试修复)
   N 个文件           0-1 轮              M 个文件          1-K 轮
   = N 轮            (通常内化在思考中)    = M 轮           (测试+修复循环)
```

**关键依赖关系：**

- 阶段 1→2→3→4 是严格串行的
- 阶段内部，部分操作可以并行（如同时读多个文件）
- 阶段 4 可能触发回到阶段 3 的循环（测试失败→修复→重测）

### 并行压缩率

理论上并行调用可以压缩轮次，但实际压缩率受限于数据依赖、上下文窗口、决策依赖和模型行为倾向。

> **建议：在预估时按串行计算，把并行节省的轮次当作意外缓冲。**

## 3. 任务分类与轮次消耗

### 预估公式

对于任何任务，用这个公式拆解：

```
总轮次 = 调查轮次 + 实施轮次 + 验证轮次 + 意外缓冲
       = (要读的文件数) + (要改的文件数) + (测试修复循环数) + ceil(前三项之和 × 0.3)
```

### 按任务类型的轮次参考表

#### Tier 1: 单点修改（5-8 轮）

典型场景：改一个函数签名、修一个 bug、加一个配置项

| 阶段     | 操作                              | 轮次    |
| -------- | --------------------------------- | ------- |
| 调查     | 读目标文件 + find_usages 查调用方 | 2-3     |
| 实施     | 改目标文件 + 改 1-3 个调用方      | 2-4     |
| 验证     | 跑测试 + 可能修 1 个失败          | 1-2     |
| **合计** |                                   | **5-8** |

你的观察 "简单的类型变更实际 5-8 轮" 完全符合这个模型。

#### Tier 2: 单模块改动（8-15 轮）

典型场景：给一个模块加新功能、重构一个类的内部实现

| 阶段     | 操作                                | 轮次     |
| -------- | ----------------------------------- | -------- |
| 调查     | 读 3-5 个相关文件 + 查依赖关系      | 4-6      |
| 实施     | 改/新建 3-5 个文件                  | 3-5      |
| 验证     | 跑测试 + 修 1-2 个失败 + 可能补测试 | 2-4      |
| **合计** |                                     | **8-15** |

#### Tier 3: 跨模块重构（15-30 轮）

典型场景：抽象公共接口、迁移 API 模式、改数据流

| 阶段     | 操作                                              | 轮次      |
| -------- | ------------------------------------------------- | --------- |
| 调查     | 读 5-10 个文件 + 多次 find_usages/find_definition | 6-10      |
| 实施     | 改 5-10 个文件（可能分多个子阶段）                | 5-10      |
| 验证     | 跑测试 + 修 2-5 个失败 + 回归测试                 | 4-8       |
| **合计** |                                                   | **15-30** |

你的观察 "跨模块重构 20-40 轮" 也符合——上限超过 30 是因为意外复杂度（发现未预期的依赖、legacy 代码等）。

#### Tier 4: 架构级变更（30-60+ 轮）

典型场景：认证系统迁移、数据库 schema 重构、新增完整子系统

这类任务通常需要拆成多个 Tier 2-3 的子任务，每个子任务有自己的 reminder 周期。

### 关键洞察：轮次消耗的非线性

轮次消耗不是线性增长的。随着任务复杂度上升，**意外缓冲占比应该增大**：

| 任务 Tier | 基础轮次 | 建议缓冲系数 | 含缓冲总轮次 |
| --------- | -------- | ------------ | ------------ |
| Tier 1    | 4-6      | ×1.3         | 5-8          |
| Tier 2    | 7-12     | ×1.3         | 9-15         |
| Tier 3    | 12-22    | ×1.4         | 17-30        |
| Tier 4    | 25-40    | ×1.5         | 38-60        |

原因：复杂度越高，"未知的未知"越多。Tier 1 的意外通常是"多了几个调用方"，Tier 3 的意外可能是"发现一个完全没预料到的子系统依赖"。

## 4. Reminder Delay 方法论

### Delay 不是"预计完成时间"，而是"检查点间隔"

这是一个关键的心智模型转换。很多人（包括 LLM）把 delay 理解为"我预计 N 轮完成，所以 delay=N"。但更好的理解是：

> **delay = 你愿意在没有反思的情况下连续执行多少轮**

这两个理解的区别：

- "预计完成时间"思维 → delay 偏大，因为你想在完成时触发 → 如果预估错了，你在错误方向上走了很远才发现
- "检查点间隔"思维 → delay 偏小，因为你想频繁检查 → 即使预估错了，偏差也被限制在一个小窗口内

### Delay 设置的决策框架

```
                    ┌─ 置信度高（做过类似任务）─→ delay = 基础轮次 × 0.7
                    │
任务预估轮次 N ──────┤
                    │
                    └─ 置信度低（首次/不确定）──→ delay = min(N × 0.5, 5)
```

**具体建议：**

| 任务 Tier       | 预估总轮次 | 建议首次 delay | 理由                                |
| --------------- | ---------- | -------------- | ----------------------------------- |
| Tier 1 (5-8r)   | 5-8        | 3-4            | 短任务，一个检查点足够              |
| Tier 2 (8-15r)  | 8-15       | 4-5            | 调查阶段结束时触发第一次检查        |
| Tier 3 (15-30r) | 15-30      | 5-7            | 分 3-5 个检查点，每个覆盖一个子阶段 |
| Tier 4 (30-60r) | 30-60      | 5-7            | 同上，但需要更多检查点              |

**注意 Tier 3-4 的 delay 并没有随总轮次线性增长。** 这是有意的——越大的任务，越需要频繁检查方向是否正确。delay 的上限建议不超过 7。

### 为什么 delay 上限是 7？

1. **认知窗口**：7 轮之后，agent 对最初计划的记忆开始模糊（尤其在长上下文中）
2. **纠错成本**：如果方向错了，7 轮的返工成本还可以接受；15 轮的返工成本很高
3. **校准频率**：更频繁的检查点 = 更快的预估校准收敛

### 后续 delay 的动态调整

第一次 reminder 触发后，后续 delay 应该基于实际数据调整：

```
实际进度率 = 已完成工作量 / 已消耗轮次
剩余轮次估计 = 剩余工作量 / 实际进度率
下一个 delay = min(剩余轮次估计 × 0.7, 7)
```

这就是你的 prompt 中已经体现的"校准"思想，但需要在示例中更显式地展示这个计算过程。

## 5. Few-Shot 示例校准

### 示例是 LLM 学习预估的主要信号源

LLM 不会从抽象规则中学会预估——它从示例中的具体数字建立"锚点"。如果你的示例中：

- 长任务示例的 delay=4，LLM 会认为 4 是"大任务的合理 delay"
- 短任务示例的 delay=3，LLM 会认为 3 是"小任务的合理 delay"

这意味着 **示例中的数字比规则描述更有影响力**。

### 当前示例的校准问题

分析你当前的两个示例：

**长任务示例（支付模块重构）：**

- 预估 "12+ 轮"，首次 delay=4 ✅ 这个比例合理
- 但示例中的 Phase 1 "est. 3r" 偏低——读现有结构 + 识别公共接口 + 设计 PaymentProvider，至少需要读 3-4 个文件 + 可能 find_usages 1-2 次 = 5-6 轮
- Phase 2 "est. 7r" 也偏低——3 个适配器 × (读+改) + 迁移调用方 = 至少 9-12 轮

**短任务示例（unknown→string）：**

- delay=3 ✅ 合理
- 但示例说 "1r actual"——这暗示一轮就能完成改签名 + find_usages + 逐一更新 + 测试。实际上这至少需要 3-4 轮（find_usages 1轮 + 改 2-3 个文件 2-3 轮 + 跑测试 1 轮）
- "1r actual vs 3r est" 这个对比会教 LLM "3 轮的预估其实 1 轮就够了" → 强化低估

### 校准原则

**原则 1：示例中的预估数字必须接近真实值**

不要为了展示"校准能力"而故意写一个偏高的预估然后提前完成。LLM 会从中学到错误的基准线。

**原则 2：示例中要显式展示"数文件/数操作"的思考过程**

```
# 差的预估思考
"小任务——改签名、查调用方、更新、测试。预计 1-2 轮。"

# 好的预估思考
"改签名(1r) + find_usages(1r) + 更新调用方(假设3个=2r，可能并行) + 跑测试(1r) = 5r 基础。
 置信度中等（不知道有多少调用方），delay=3 作为首个检查点。"
```

**原则 3：示例要覆盖"预估偏低后的修正"场景**

这比"提前完成"的场景更有教学价值，因为偏低是更常见的情况。展示：

1. 预估 X 轮
2. Reminder 触发时发现只完成了 60%
3. 分析原因（"调用方比预期多"/"发现了未预期的依赖"）
4. 基于实际数据重新预估

**原则 4：提前完成的示例中，actual 和 est 的差距不要太大**

"5r actual vs 7r est" 比 "1r actual vs 3r est" 更真实，也更有教学价值。

## 6. 具体改进建议

### 6.1 对 reminder.ts 描述文本的改进

当前描述中的问题：

**问题 A：示例 delay 数字偏低**

当前第一个示例：

```
reminder({ content: "Phase 1 Investigate (est. 3r):...\nPhase 2 Implement (est. 7r):...", delay: 4 })
```

Phase 1 "est. 3r" 意味着读结构+识别适配器+设计接口只需 3 轮。但实际上：

- 读模块结构：2-3 个文件 = 2-3r
- 识别适配器：find_usages/find_definition = 1-2r
- 设计接口：可能内化在思考中 = 0r

所以 Phase 1 实际 ~4-5r。建议改为 "est. 5r"。

Phase 2 "est. 7r" 意味着实现 3 个适配器 + 迁移调用方只需 7 轮。但实际上：

- 每个适配器：读旧代码(1r) + 写新适配器(1r) = 2r × 3 = 6r
- 迁移调用方：find_usages(1r) + 改调用方(2-3r) = 3-4r
- 跑测试 + 修复：2-3r

所以 Phase 2 实际 ~11-13r。建议改为 "est. 12r"。

**问题 B：短任务示例的 delay=3 合理，但描述暗示 1 轮完成**

当前第二个示例：

```
reminder({ content: "unknown→string:\n[ ] change signature [ ] update callers [ ] run tests\n...", delay: 3 })
```

delay=3 本身合理。但描述中 "If this fires → scope expanded" 暗示 3 轮内应该完成。实际上 3 轮可能刚好够（改签名 1r + 更新调用方 1-2r + 测试 1r = 3-4r），所以 delay=3 更像是"第一个检查点"而非"应该完成的时间"。建议在描述中明确这一点。


## 7. 权衡与不确定性

### 我确信的

1. **预估偏低是系统性的，不是偶然的。** 这在软件工程和 LLM agent 领域都有充分的经验证据。
2. **"数工具调用"比"数概念步骤"更准确。** 这是从你的执行模型（1轮=1个主要动作）直接推导出的。
3. **示例中的数字比规则描述更能影响 LLM 行为。** 这是 few-shot learning 的基本特性。
4. **Delay 上限不应超过 7。** 这是基于纠错成本和认知窗口的实践经验。

### 我不确定的

1. **具体的轮次数字因模型而异。** 不同的 LLM（Claude vs GPT-4 vs Gemini）在工具调用模式上有差异——有些更倾向于并行，有些更保守。我给出的数字基于"保守串行"假设，实际可能因模型而有 ±20% 的偏差。

2. **并行压缩率的实际值。** 我说"0.7-0.9"是基于一般经验，但你的具体 agent 框架中，模型实际并行调用的频率可能不同。建议你收集实际数据来校准。

3. **Few-shot 示例的最优数量和格式。** 你当前有 2 个 reminder 示例（长+短），这可能足够也可能不够。如果模型仍然低估，可能需要加入第 3 个"中等任务"示例来覆盖 Tier 2 场景。但更多示例 = 更多 token 消耗，这是一个权衡。

### 关键权衡

**权衡 1：预估准确性 vs Token 消耗**

更详细的预估思考过程（"数文件、数操作"）会消耗更多 token，但能产生更准确的预估。如果你的 agent 运行在 token 敏感的环境中，可能需要在预估详细度和 token 效率之间找平衡。

建议：预估思考的 token 成本相对于错误预估导致的返工成本来说微不足道。优先准确性。

**权衡 2：Delay 偏短 vs 偏长**

- Delay 偏短：更频繁的反思 → 更好的方向控制，但每次 reminder 触发都会打断执行流，增加 1 轮开销（处理 reminder + 设新 reminder）
- Delay 偏长：更少的中断 → 更流畅的执行，但方向偏差的发现更晚

建议：偏短更安全。每次 reminder 的开销是 1 轮，但方向错误的返工成本可能是 5-10 轮。

**权衡 3：示例的真实性 vs 教学效果**

完全真实的示例可能很长（20+ 轮的完整执行过程），不适合放在 prompt 中。你需要在"足够真实以建立正确锚点"和"足够简洁以节省 token"之间找平衡。

建议：示例不需要展示完整执行过程，但**数字必须真实**。可以用省略号跳过中间步骤，但预估数字、delay 值、actual vs estimated 的对比必须反映真实的轮次消耗模式。

## 附录：快速参考卡

### 预估速查表

```
要读 N 个文件        → N 轮（可能并行压缩到 ceil(N/2)，但别指望）
要改 M 个文件        → M 轮（几乎不可并行，因为有依赖）
要跑测试 + 修复      → 2-3 轮（1轮跑 + 1-2轮修）
find_usages/定义     → 每次 1 轮
用户交互             → 2 轮（问 + 处理回答）
```

### Delay 速查表

```
Tier 1 (5-8r):   delay = 3-4
Tier 2 (8-15r):  delay = 4-5
Tier 3 (15-30r): delay = 5-7
Tier 4 (30-60r): delay = 5-7（分多个 phase，每个 phase 一个 reminder）
最大 delay:       7（硬上限）
```

### 预估思考模板

```
[预估]
调查：读 X 个文件 + Y 次查引用 = (X+Y)r
实施：改 Z 个文件 = Zr
验证：测试 + 修复 = 2-3r
基础：(X+Y) + Z + 3 = Nr
缓冲：ceil(N × 0.3) = Br
总计：~(N+B)r，置信度 [高/中/低]
首次 delay = min(ceil(N × 0.5), 7) 如果置信度低
首次 delay = min(ceil(N × 0.7), 7) 如果置信度高
```
