# 在 Agent 工具使用 Few-Shot 中实现 Deep→Reflect→Explore 振荡结构

> 技术咨询备忘录 | 2026-03-02
> 主题：reminder 元认知工具的 few-shot 示例振荡设计

---

## 〇、诊断：你的示例为什么是"伪振荡"

先看你当前长任务示例的行为序列：

```
Deep → Reflect → reminder() → Deep → ... → [触发] → Reflect → Explore → Deep → reminder() → ...
```

表面上有 [Deep] [Reflect] [Explore] 标签，但仔细看行为的**因果关系**：

1. **每个标签都在"该出现的地方"出现**——Deep 在分析时出现，Reflect 在 reminder 触发后出现，Explore 在需要做选择时出现。这不是振荡，这是**剧本**。真正的振荡意味着推理行为的出现是被**认知需要**驱动的，而非被**流程节点**驱动的。

2. **Reflect 只在两个位置出现**：设 reminder 之前（"长任务最大的风险是上下文漂移"）和 reminder 触发之后（"回顾这个阶段"）。这两个位置恰好是流程规定的"该反思的地方"。但真正的反思应该在**任何认知不确定性出现的地方**自发产生——比如在预估工作量时质疑自己的预估依据，在选择 delay 值时质疑这个数字的合理性。

3. **Explore 只出现一次**，且出现在一个"经典选择题"位置（webhook 验证放哪里）。但探索不只是"面对选择时列选项"——它还应该出现在**重新框定问题**的时刻，比如"我预估 12+ 轮，但也许这个任务根本不应该一次性做完？"

4. **转移模式过于规整**：Deep→Reflect→Tool→Deep→...→Reflect→Explore→Deep→Tool。现实中的认知过程是：Deep→Deep→"等一下"→Reflect→Deep→"也许..."→Explore→Reflect→Deep。振荡的特征是**不可完全预测下一个行为类型**，而你的示例中每个行为类型的出现都可以从流程图上预测。

**根本原因**：你是先画了 reminder 的工作流程图（预估→设置→执行→触发→反思→重设），然后在流程节点上"贴"行为标签。这产生的是**流程驱动的伪振荡**，而非**认知驱动的真振荡**。

## 一、核心洞察：Agent 场景的振荡与数学证明场景的本质差异

论文的分子结构理论来自数学证明场景。在那个场景中，振荡的驱动力是**逻辑不确定性**——"我不确定这个引理是否成立"触发 Reflect，"也许可以用另一个定理"触发 Explore。但在 agent 工具使用场景中，振荡的驱动力完全不同。理解这个差异是设计有效振荡的前提。

### 1.1 数学场景 vs. Agent 场景的振荡驱动力对比

| 维度                 | 数学证明场景                 | Agent 工具使用场景                                           |
| -------------------- | ---------------------------- | ------------------------------------------------------------ |
| **Deep 的对象**      | 逻辑推导（引理→定理）        | 环境理解（代码→意图→方案）                                   |
| **Reflect 的触发**   | 逻辑矛盾或不确定性           | **预估与现实的偏差**、假设未验证、用户意图不确定             |
| **Explore 的触发**   | 当前证明路径受阻             | **方案空间未充分搜索**、存在未考虑的约束、工具选择的替代方案 |
| **振荡的粒度**       | 推理步骤级（每几步振荡一次） | **决策点级**（每个需要做选择的地方振荡一次）                 |
| **Normal Operation** | 算术计算、事实回忆           | 工具调用执行、文件读写、命令运行                             |

### 1.2 Agent 场景中振荡的三个独特驱动力

**驱动力 A：预估不确定性（Estimation Uncertainty）**

这是 reminder 场景最核心的振荡源。每次你做预估（工作量、复杂度、delay 值），都存在一个天然的 Deep→Reflect 振荡机会：

```
[Deep] 这个任务涉及 3 个适配器，预估 12 轮。
[Reflect] 等一下——我还没读过代码，12 这个数字是从哪来的？是基于"3 个适配器 × 4 轮/适配器"的粗算。但我不知道这些适配器的复杂度是否均匀。也许支付宝很简单但 Stripe 的 webhook 很复杂。
[Deep] 那我应该把 delay 设短一点（5 轮而非 7 轮），这样如果预估偏差大，能更早触发反思。
```

这里的振荡不是"流程规定你该反思了"，而是"你做了一个预估，然后你的认知系统自然地质疑了这个预估的依据"。

**驱动力 B：工具选择的元认知（Tool-Choice Metacognition）**

Agent 场景独有的振荡源：不只是"用什么工具"，而是"我为什么选这个工具而不是那个"。对于 reminder 这种元认知工具，这个振荡尤其重要：

```
[Deep] 任务很小，改个类型签名，预计 1-2 轮。
[Reflect] 我要不要设 reminder？规则说所有任务都要设。但这个任务可能 1 轮就完了，设 reminder 的认知开销可能比任务本身还大。
[Deep] 不对——reminder 的价值不只是"提醒我"，还有"如果触发了说明预估错了"。即使任务很小，设一个 delay=3 的 reminder 也是在给自己一个"预估校准信号"。
```

**驱动力 C：环境反馈的认知冲突（Cognitive Conflict from Environment）**

Agent 与环境交互后获得的信息可能与预期不符，这是最自然的振荡触发点：

```
[Deep] 按计划读取支付模块结构。
[执行工具：读取文件]
[Deep] 发现有 3 个适配器文件，但还有一个 legacy_payment.ts 没在文档里提到。
[Reflect] 这改变了我的预估——不是 3 个适配器，可能是 4 个，而且 legacy 的那个可能有特殊的历史包袱。我之前设的 delay=5 可能不够。
[Explore] 两种处理方式：(A) 把 legacy 也纳入重构范围，delay 改大；(B) 先忽略 legacy，在 reminder 触发时再评估。B 更稳妥——先做确定的部分，用 reminder 触发点来决定是否扩大范围。
```

### 1.3 关键认知转换

从数学场景迁移到 agent 场景，你需要做的核心认知转换是：

> **振荡不是"在流程节点上贴标签"，而是"在每个认知不确定性出现的地方，让推理自然地折叠回去检查自己"。**

在 agent 场景中，认知不确定性主要来自三个地方：

1. **你做了一个预估**（任何预估都有不确定性）
2. **你做了一个选择**（任何选择都排除了替代方案）
3. **环境给了你新信息**（新信息可能与假设冲突）

这三个地方就是振荡的天然节点。

### 关键观察

**你当前的示例只在节点 5（reminder 触发）处有真正的振荡。** 节点 1-4 和 6-7 都是线性推进的。这就是为什么整体感觉是"线性流程 + 两个反思点"而非"持续振荡"。

**并非所有 7 个节点都需要在每个示例中展示。** 但一个好的长任务示例应该至少覆盖 4-5 个振荡节点，让模型学到"振荡可以在任何认知不确定性出现的地方发生"，而非"振荡只在 reminder 触发时发生"。

### 节点之间的依赖关系

```
节点 1 ──串行──→ 节点 2 ──串行──→ 节点 3 ──串行──→ [执行]
                                                      │
                                              节点 4 可在执行中
                                              任意时刻出现（事件驱动）
                                                      │
                                                      ▼
节点 5 ──串行──→ 节点 6 ──串行──→ [继续执行] ──→ 节点 7
```

节点 4 是唯一的**事件驱动**节点——它不在固定位置出现，而是在环境反馈与预期不符时随时触发。这也是最能体现"真振荡"的节点，因为它的出现位置不可预测。

## 三、方法论框架：从线性示例到振荡示例的 5 步改造法

### 步骤 1：标记你现有示例中的每个"决策点"

决策点 = 你做了预估、做了选择、或收到了新信息的地方。在你当前的长任务示例中：

- "预计 12+ 轮" → 决策点（预估）
- "先设 reminder 锚定计划" → 决策点（选择）
- "delay: 5" → 决策点（预估）
- "比预估快了" → 决策点（新信息）
- "webhook 签名验证比较特殊" → 决策点（新信息）
- "选 A，调整接口设计" → 决策点（选择）
- "预计 5 轮" → 决策点（预估）

你有 7 个决策点，但只有 2 个有振荡。

### 步骤 2：为每个决策点写一个"质疑句"

质疑句是触发 Reflect 或 Explore 的种子。格式："我刚才做了 X，但 Y 是否成立？"

- "预计 12+ 轮" → "我还没读代码，12 这个数字的依据是什么？"
- "delay: 5" → "不确定性这么高，delay 应该短一点还是长一点？"
- "比预估快了" → "快了是好事，但是否因为我跳过了某些步骤？"

### 步骤 3：选择 4-5 个最有教学价值的决策点展开振荡

不是每个决策点都需要展开——过度振荡会导致示例冗长且模型学到"每句话都要质疑"（overthinking）。选择标准：

- **优先展开预估类决策点**：因为 reminder 的核心价值就是校准预估
- **优先展开有认知冲突的决策点**：环境反馈与预期不符
- **跳过显而易见的决策点**：如果选择很明确，不需要振荡

### 步骤 4：用转移矩阵检查行为序列

写完后，提取行为序列，检查：

- Deep 是否占 40-50%？
- Reflect 是否占 15-25%？
- Explore 是否占 10-20%？
- Deep→Deep 是否是最常见的转移？
- Reflect 后是否大概率回到 Deep？

### 步骤 5：验证"反思回连"

每个 Reflect 步骤是否明确引用了之前的某个具体推理内容？如果 Reflect 只是泛泛地说"让我想想"，那不是真正的反思——真正的反思必须**折叠回**之前的某个具体节点。

## 四、声明式→行动式：Reminder 规范文本的改写原则

你当前的规范文本有两个问题：

### 问题 A：声明式描述对模型无效

当前写法：

> "它是你的工作节奏锚点，驱动'预估→执行→反馈反思→重新评估'的循环"

这告诉模型 reminder **是什么**，但模型需要知道的是 **怎么用、用了会怎样**。

**改写原则：每句话必须能回答 "so what?" 测试。**

| 声明式（❌）                                         | 行动式（✅）                                           |
| ---------------------------------------------------- | ------------------------------------------------------ |
| "它是你的工作节奏锚点"                               | "收到任务后，先预估工作量，然后立即设 reminder"        |
| "每两个相邻 reminder 之间就是一个工作阶段"           | "reminder 触发时，对比计划 vs 实际，找出偏差原因"      |
| "你的认知从'之前几轮'变成'reminder #N 到 #N+1 之间'" | "在 reminder content 中写下 checklist，触发时逐项检查" |

### 问题 B：规则列表缺少"为什么"

当前写法：

> "收到任务后立即预估并设 reminder #1——调研本身是计划中的一步，不是计划的前提"

这个规则本身是对的，但模型不知道**违反它会怎样**。行动导向的描述应该包含后果：

> "收到任务后立即预估并设 reminder #1。不要等调研完再设——调研是计划的一步。如果你等调研完，就失去了用 reminder 校准调研耗时的机会。"

### 改写公式

```
声明式: [主语] 是 [定义]
行动式: 当 [触发条件] 时，做 [具体动作]，因为 [不做的后果]
```

这个公式直接对应论文中 Deep Reasoning 的特征——"步骤之间有明确的逻辑依赖关系"。行动式描述天然携带因果链（触发→动作→后果），而声明式描述只有定义，没有因果。

## 五、完整改造示例：长任务 Reminder 的振荡版

以下是对你当前长任务示例的改造，覆盖节点 1、2、4、5、6 的振荡。标注了每个振荡点的节点编号。

```
user: 帮我重构这个支付模块，把所有第三方支付渠道抽象成统一接口

A: [Deep] 跨多文件重构——支付宝、微信、Stripe 三个渠道。
需要调研→设计→逐个迁移。粗估 12+ 轮。

[Reflect] 等一下——12 这个数字哪来的？                    ← 节点1
我还没读过代码，是按"3渠道×4轮"粗算的。

粗估的置信度很低，delay 应该偏短，让校准信号来得早一点。

[Deep] 把调研作为计划第一步，delay 设 4 而非 7。         ← 节点2
如果 4 轮后调研还没完，说明复杂度超出预期，
正好用触发点来重新评估。

[工具调用] reminder({

    [ ] 支付宝 [ ] 微信 [ ] Stripe [ ] 迁移调用方\n

没在文档里提到。

legacy 的那个可能有历史包袱。我的预估基础变了。

[Explore] 两条路：
(A) 把 legacy 纳入重构，扩大范围；
(B) 先做确定的 3 个，在 reminder 触发时再评估 legacy。
B 更稳妥——用 reminder 触发点作为决策门控。

[Deep] 选 B，继续设计接口，实现支付宝和微信适配器...

[Reflect] 对比计划 vs 实际：                              ← 节点5

[工具调用] reminder({

    [ ] Stripe（注意 webhook 验证）\n
    [ ] 决定 legacy_payment.ts 的处理方式\n
    [ ] 迁移调用方 [ ] 测试 + 清理",
  delay: 4
})

[继续执行...]
```

### 行为序列分析

```
Deep → Reflect → Deep → Tool → Deep → Tool →
Deep → Reflect → Explore → Deep → ... →
[触发] → Reflect → Deep → Reflect → Tool → ...
```

- Deep: 8 次 (~53%) — 占主体 ✓
- Reflect: 5 次 (~33%) — 略高，可接受（元认知工具示例需要更多反思）
- Explore: 1 次 (~7%) — 偏低但合理（长任务示例中探索集中在关键分叉点）
- 转移模式：Deep→Reflect 出现 4 次，Reflect→Deep 出现 3 次 — 振荡明显 ✓
- 反思回连：每个 Reflect 都明确引用了之前的具体内容 ✓

## 六、检查清单与权衡

### 检查清单

**振荡质量**

- [ ] 每个 Reflect 是否由认知不确定性驱动（而非流程节点驱动）？
- [ ] 每个 Reflect 是否明确折叠回了之前的某个具体推理内容？
- [ ] Explore 是否出现在真正的分叉点（而非装饰性的"列选项"）？
- [ ] 振荡节点是否覆盖了 reminder 生命周期的多个阶段（而非只在触发时）？

**行为分布**

- [ ] Deep 占 40-55%？（元认知工具示例中 Reflect 占比会偏高，Deep 可略低于 50%）
- [ ] Reflect 占 20-30%？
- [ ] Explore 占 5-15%？
- [ ] Deep→Deep 是最常见的转移？
- [ ] 不存在 Explore→Explore 的连续转移？（那是语义漂移的信号）

**规范文本**

- [ ] 每句话通过 "so what?" 测试？
- [ ] 规则格式为"当 X 时，做 Y，因为 Z"？
- [ ] 没有纯声明式定义（"它是..."）？

### 权衡与边界

| 权衡              | 偏向振荡                                       | 偏向简洁                                    |
| ----------------- | ---------------------------------------------- | ------------------------------------------- |
| 示例长度          | 更多振荡节点 = 更长的示例 = 更多 token         | 更短 = 更省 token，但模型学到的振荡模式更少 |
| 教学覆盖          | 覆盖 5+ 节点让模型学到"振荡可以在任何地方发生" | 覆盖 2-3 节点足以传达基本模式               |
| overthinking 风险 | 过多振荡会教模型"每句话都要质疑自己"           | 过少振荡会教模型"只在固定点反思"            |

**建议的平衡点**：长任务示例覆盖 4-5 个振荡节点，短任务示例覆盖 1-2 个。这样模型既学到振荡的多样性，又不会过度泛化。

### 一个容易忽略的陷阱

**不要让振荡变成表演。** 如果你为了凑振荡比例而在不需要质疑的地方强行插入 Reflect，模型会学到"Reflect 是一种装饰"而非"Reflect 是认知需要的产物"。判断标准很简单：**删掉这个 Reflect，推理结论会变吗？** 如果不会变，这个 Reflect 就是装饰性的，应该删掉。
